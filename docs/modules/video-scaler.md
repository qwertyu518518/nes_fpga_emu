# 视频 scaler：软件 framebuffer / SDL blit 与硬件 frame buffer 的对应

本文说明 `rtl/nes_core/video/nes_video_scaler.v` 的接口合同、数据流和**它现在到底是什么、又不是什么**，并回答一个教学问题：

> 一个用 C 写的软件模拟器（PPU 每 dot 往 `framebuffer[y][x]` 写一个调色板索引，帧末一次性 `SDL_BlitSurface` / `SDL_UpdateTexture`）和一个用 Verilog 写的硬件实现（RAM + 自由运行的读指针 + 2×2 地址复制 + VGA 侧像素流），是不是**同一套行为的两种写法**？

结论：**方向是同一套，但本模块只实现了其中最容易被误解的那一小块。** 软件模拟器把"渲染"和"显示"分成两个阶段（先整帧算完，再整帧 blit），因为 CPU 是顺序执行的；真实硬件必须让"生成"和"读出"**同时**进行，因为显示端有自己不可暂停的时序。本模块实现的是**硬件那一侧的骨架**（一个 256×240 RGB565 帧缓冲 + 一个自由运行的 2 倍读指针），但它**没有任何时序发生器**（没有 HS/VS/DE、没有消隐、没有黑边），所以它现在还**不能**直接驱动显示器。

`docs/modules/ppu-sprites.md` 讲的是另一种"软件状态机 vs 硬件并行"的对应（OAM 评估）。本文讲的是"软件 framebuffer vs 硬件行/帧缓冲"的对应，两者的关键差别是**谁决定读出节奏**。

---

## 1. 术语与数据规模

| 名称 | 规模 | 说明 |
|---|---|---|
| 源分辨率 | 256 × 240 = 61,440 像素 | NES 可见区，每像素 1 个 4 位调色板索引 |
| 本模块帧缓冲 | 61,440 × 16 bit = **983,040 bit ≈ 120 KiB** | 存的是查表后的 RGB565，不是索引 |
| 2 倍输出分辨率 | 512 × 480 = 245,760 像素 | 靠**地址右移一位**得到，不是靠插值 |
| EP4CE10 全部片上存储 | 423,936 bit ≈ 51.75 KiB | Fitter 报告数字，见 `docs/hardware/01-ep4ce10-board.md` 第 1.1 节 |

**本模块的帧缓冲比整片 FPGA 的片上存储还大 2.3 倍。** 这是本文最重要的一条结论，第 5 节展开。

## 2. 软件模拟器怎么显示一帧

### 2.1 两阶段模型

一个典型的 C NES 模拟器（`.slim/clonedeps/repos/caseif__cNES/`、`.slim/clonedeps/repos/ObaraEmmanuel__NES/` 都是这种结构）显示一帧的流程是：

```text
阶段 A（生成，慢，顺序）：PPU 跑 341×262 个 dot，每 dot 算出一个 4 位索引
                          → framebuffer[y][x] = index        （61,440 次写）
阶段 B（显示，快，批量）：帧末一次性把 framebuffer 查表成像素并 blit
                          → SDL_UpdateTexture / glTexSubImage2D
```

软件模拟器的两个"显示器"是这样诞生的：

| 软件概念 | 数据 | 谁决定节奏 |
|---|---|---|
| `framebuffer[240][256]` | 4 位索引或 8/16/32 位像素 | PPU dot 循环（**生成侧**） |
| `SDL_Texture` / `GLuint` | RGB565/RGBA8 | 每帧一次 `SDL_RenderPresent`（**显示侧**） |

### 2.2 关键性质：软件侧**不需要**读指针

软件模拟器在阶段 A 结束时，整个 framebuffer 已经是"最终画面"，blit 只是一次**从左到右、从上到下的顺序内存遍历**。遍历的起点和步长由 blit 库决定，不是被测逻辑的一部分。

**所以软件模拟器里根本没有"读指针"这个概念**——这是初学者最容易漏掉的一步。硬件必须显式造一个：

```text
软件： for (y) for (x) blit(framebuffer[y][x]);   ← 遍历顺序是代码写死的
硬件： <必须有一个寄存器> scan_x, scan_y         ← 每拍 +1，硬件不能"遍历"
```

硬件里这个寄存器就是本模块的 `scan_x` / `scan_y`。它不是"多余的硬件"，它是软件 `for` 循环的硬件等价物。

## 3. 本模块的实际合同

### 3.1 写口：PPU 侧

```verilog
input  wire        pixel_valid;
input  wire [7:0]  in_pixel_x;
input  wire [7:0]  in_pixel_y;
input  wire [3:0]  in_pixel_index;
```

在 `pixel_valid` 为高的那个 `posedge`，模块执行：

```verilog
frame_mem[{in_pixel_y, in_pixel_x}] <= palette_rgb565(in_pixel_index);
```

对应关系：

| 软件 | 硬件 | 差别 |
|---|---|---|
| `framebuffer[y][x] = index` | `frame_mem[{y, x}] <= pal(idx)` | 硬件**存的是 RGB565**，调色板查表被**提前**到写口 |
| `SDL_BlitSurface` 时查表 | `palette_rgb565()` 函数 | 查表从"显示侧"搬到了"生成侧" |

这个搬家是必须的：VGA 侧的像素流每个像素只有一拍，没有时间再查一次表。软件侧则相反——blit 库查表很便宜。**"查表放在哪一侧"是软件和硬件最实质的一处差异。**

`{in_pixel_y, in_pixel_x}` 是一个 16 位拼接地址，语义就是 `y * 256 + x`，所以 `frame_mem` 正好是 `[0:61439]` = 240×256 项。宽度选择是刻意的：y 8 位 + x 8 位，不需要除法器。

### 3.2 行/帧计数：软件里没有的东西

```verilog
if (line_count == 8'd255) begin          // LINE_LAST
    line_ready <= 1'b1;
    if (frame_line_count == 8'd239)      // FRAME_LAST
        frame_ready <= 1'b1;
```

| 信号 | 含义 | 触发条件 |
|---|---|---|
| `line_ready` | 一行 256 个像素收齐了 | 第 256 个 `pixel_valid` 之后的**下一个**周期，单周期脉冲 |
| `frame_ready` | 一帧 240 行收齐了 | 第 240 次 `line_ready` 的**同一个**周期，单周期脉冲 |

**为什么软件模拟器不需要这两个信号？** 因为软件模拟器的 PPU 循环本身就是"跑完 256 个 dot 就 `y++`"的结构，行边界和帧边界是**控制流的一部分**，不需要对外宣布。硬件里 PPU 是自由运行的独立时基，帧缓冲只能通过握手知道"这一行可以读走了"。

`line_ready` / `frame_ready` 就是硬件版的 `y++` / 帧末标志。**它们是给下游（行缓冲填充器、SDRAM 写 burst、VGA 帧交换）用的**，不是给本模块自己用的——本模块的读指针完全不理它们（见 3.3）。

`tb_nes_video_scaler.v` 的 `write_frame` task 逐像素检查这两个脉冲的位置（第 256 个 / 第 240×256 个），并检查 `line_ready` 不会连续两拍为高。

### 3.3 读口：VGA 侧，以及"自由运行"这件事

```verilog
assign scan_line_last = (scan_x == 10'd511);
assign scan_x_next    = scan_line_last ? 10'd0 : (scan_x + 10'd1);
assign scan_y_next    = scan_line_last ? ((scan_y == 10'd479) ? 10'd0 : (scan_y + 10'd1)) : scan_y;
```

三个必须知道的事实：

1. **读指针是自由运行的**，与 `line_ready` / `frame_ready` 无关，也与 `pixel_valid` 无关。它从复位开始就每拍 +1，绕 512×480 一圈是 245,760 拍，按 25 MHz 算是 **9.83 ms** 一圈（对比：VGA 的一帧是 800×525 = 420,000 拍，约 16.8 ms 一帧 / 59.52 Hz）。
2. **`out_pixel_x` / `out_pixel_y` / `rgb565` 是对齐的**。三个输出都从同一个 `scan_x`/`scan_y` 当前值取值，所以下游拿到的一组三元组一定描述同一个源像素。
3. **输出里没有 `valid` 信号**。模块假定下游每拍都接收一个像素，512×480 全部是有效像素。VGA 的消隐期怎么办？——**这个模块不管**，见第 4 节。

自由运行是有意的还是缺陷？这取决于下游：

| 下游 | 自由运行是否可用 |
|---|---|
| 后面接一个 VGA 时序发生器，自己在消隐期拉无效 | 可以。发生器用 `out_pixel_x/y` 决定"现在该不该取这一拍" |
| 后面直接接 RGB 565 引脚 | 不行。消隐期会输出有效区第 512 列的数据，图像会横向错位 |

**自由运行 + 无 `valid` 的组合，等于把"什么时候该输出"的责任完全推给了下游。** 这是当前模块最重要的接口缺口。

### 3.4 2×2 复制：地址右移，不是数据复制

```verilog
assign mem_read_addr = {scan_y[8:1], scan_x[8:1]};
```

这一行**就是**整个 2 倍放大。没有乘法器、没有插值、没有行缓冲，就是把坐标的最低位丢掉：

| 输出坐标 | 读到的源地址 |
|---|---|
| `(0,0) (1,0) (0,1) (1,1)` | `frame_mem[0]` |
| `(2,0) (3,0) (2,1) (3,1)` | `frame_mem[1]` |
| … | … |
| `(510,478) (511,478) (510,479) (511,479)` | `frame_mem[61439]` |

对应关系：

| 软件 | 硬件 |
|---|---|
| blit 时 `dst[2x][2y] = dst[2x+1][2y] = dst[2x][2y+1] = dst[2x+1][2y+1] = src[x][y]` | `addr = {y>>1, x>>1}`，4 拍读同一个地址 |

软件必须**写 4 次**（或者在 blit 循环里内层循环跑 2 次），因为软件有两个独立的循环变量；硬件只需**一次地址计算**，因为 4 个输出像素共用一个读端口、同一拍只能读一个地址。地址右移是这个"一次读、给 4 拍用"结构的必然结果。

`scan_x[8:1]` 只有 8 位有效：512 个输出列除以 2 = 256 个源列，正好 8 位。`scan_y[8:1]` 同理。**位宽不是巧合，是 `2×2` 这个比例的直接编码。**

NES 的整数倍缩放（2×/3×）**只需要丢低位**，所以这一招对 NES 特别合适。如果是 3 倍缩放，`scan_x / 3` 就需要一个除法器或倒数乘法表，结构和代价完全不同。

### 3.5 复位

两个 `always @(posedge clk) if (reset)` 块，同步复位，清 `scan_x` / `scan_y` / `out_pixel_*` / `rgb565` / `line_count` / `frame_line_count` / `line_ready` / `frame_ready`。

**`frame_mem` 不在复位列表里。** 这是 Verilog 的正常行为（综合出来的 BRAM 也不会被复位，否则就没有块 RAM 了），但它是一条必须写进合同的性质：复位**不会**把画面清成黑，`reset` 之后读到的还是复位前的最后一帧。`tb_nes_video_scaler.v` 的 `test_reset_mid_frame` 把这条钉死了：写 100 行 → 复位 → 源像素 `(200, 110)` 仍然是复位前那一帧的内容。

另外，复位把读指针归零这件事是 TB 用来做确定性扫描的手段（`scan_start` task 就是一个 1 拍的复位脉冲）。生产设计里不会这么做，但作为合同它是明确的、可测的。

## 4. 与 VGA 时序的对应，以及缺什么

### 4.1 软件侧的对应关系表

| 软件模拟器 | 本模块 | 真实 VGA 时序（`docs/hardware/05-vga-lcd.md`） |
|---|---|---|
| `for (y = 0; y < 240; y++)` | `scan_y` 0..479 | 场计数 0..524 |
| `for (x = 0; x < 256; x++)` | `scan_x` 0..511 | 行计数 0..799 |
| 循环体外的时间 | **不存在** | 行同步 96 + 行后沿 48 + 行前沿 16 = 160 拍/行 |
| 帧末 `SDL_RenderPresent` | `frame_ready` 脉冲 | 场同步 2 + 场后沿 33 + 场前沿 10 = 45 行/帧 |
| 无（blit 是连续的） | **无** | 有效窗口 640 宽 / 480 行 |

**这张表就是本模块的缺口清单。** 三处对不上：

1. **横向 512 vs 640。** VGA 有效区 640 宽，本模块输出 512 宽。差 128 像素 = 每边 64 像素的**黑边**，640 = 64 + 512 + 64。
2. **纵向 480 vs 480 相同，但所在位置不同。** 本模块的 480 行是**连续的**，VGA 的 480 行夹在场前/场后沿之间。
3. **完全没有时序发生器。** 没有 `hsync` / `vsync` / `de` 输出，没有消隐期的"输出黑"逻辑。

`tb_nes_video_scaler.v` 因此**只测 pixel stream**，不测任何时序：第 8 条断言显式检查输出流**恰好**是 512×480，没有黑边、没有 padding、没有 blanking。这是当前模块的真实合同，写成断言就不会被误读成"已经有 VGA 时序了"。

### 4.2 2 倍放大 vs VGA 640×480 的取舍

512×480 放大到 640×480 只能是非等比的：横向 640/512 = 1.25。1.25 = 5/4 是二进制友好的（5/4 意味着每 4 个源像素扩成 5 个），但仍然需要一个独立的缩放器，**不能**再靠地址右移。

另一种选择是让 NES 输出 256×240 → 直接放到 640×480 的正中央（左右各 192、上下各 120 全黑），只做 2×2 不做 1.25×。这个方案在 NES 上最常见：整数倍放大不会引入非等比像素，而且上下 480 正好是 VGA 的 480 行，不需要任何纵向插值。本模块的 512×480 就是这个方案里"已经放大好的那一半"。

### 4.3 撕裂：软件没有，硬件必须处理

软件模拟器几乎不可能撕裂：`SDL_RenderPresent` 在帧末一次性提交，用户看到的是完整的一帧。

硬件会撕裂。`docs/hardware/05-vga-lcd.md` 第 3.3 节说得很直接：

> 如果一帧缓冲区在 VGA 扫描中途被 NES PPU 更新，可能出现撕裂。

本模块的 `frame_mem` 是**单缓冲**、**原地覆盖**的：PPU 写第 0 行的时候，VGA 读指针可能正在读第 300 行；两帧之间没有"交换"动作。`tb_nes_video_scaler.v` 的 `test_frame_b` 明确验证了"下一帧原地覆盖当前帧"这个行为——它是当前模块的正确行为，也是撕裂的根源。

解决撕裂需要**双缓冲**（两块 120 KiB 的内存，见第 5 节）或**行缓冲**（用小块内存把"生成侧"和"显示侧"在行边界上解耦）。

## 5. 当前模块不适合 EP4CE10：BRAM 差 2.3 倍

### 5.1 数字对不上

| 项目 | 位数 | 来源 |
|---|---:|---|
| 本模块 `frame_mem` | 61,440 × 16 = **983,040 bit** | 256×240×RGB565 |
| EP4CE10 全部片上存储 | **423,936 bit** | Fitter 报告（`docs/hardware/01-ep4ce10-board.md`） |
| 差额 | 559,104 bit（约 68 KiB） | 需要外部存储 |

即使只看"能不能装下"：**装不下，而且差得不是一点。** 片上存储还有 CPU、APU、mapper ROM、OAM、tile、FIFO 全都要分，实际留给视频的也许只有三分之一。

`reg [15:0] frame_mem [0:61439]` 在 Quartus 里会被推断成 61,440/512 = **120 个 M9K 块**（EP4CE10 一共只有 46 个），综合会直接失败。

### 5.2 就算装得下，带宽也不够

`docs/hardware/04-memory-and-fifo.md` 第 7.1 节和 `docs/hardware/05-vga-lcd.md` 第 3.2 节给的口径：

```text
16 bit × 25 MHz = 50 MB/s 理论峰值
640 × 480 × 2 B × 59.52 Hz = 36.6 MB/s 原始需求
```

36.6 MB/s 确实小于 50 MB/s，**但那是 640×480 的一整帧**。本模块 512×480 加上 PPU 写侧、加上音频和 SDRAM 仲裁之后：

- PPU 写侧每帧要写 61,440 个像素（本模块是**单端口** `frame_mem`，写和读共用一个端口，需要真双端口 BRAM 或者自己分时）；
- VGA 侧一帧要读 245,760 拍，但只在 640 个有效像素窗口里用得上——**必须加时序发生器之后**才会下降到 640×480 = 307,200 有效拍；
- 加上 `docs/hardware/05-vga-lcd.md` 说的"VGA 有消隐期，不能在所有周期都假定有有效像素"；
- SDRAM 控制器、自动刷新、外设仲裁都会抢周期。

结论和仓库既有文档一致：**BRAM 带宽"能过"但余量不足，且容量先过不去。**

### 5.3 后续方案

仓库 `docs/hardware/05-vga-lcd.md` 第 3.2 节列了四种架构。对本模块的演进方向，优先级是：

| 方案 | 内存 | 对本模块的改动 | 评价 |
|---|---|---|---|
| **行缓冲**（推荐先做） | 2 行 × 640 像素 × 16 bit ≈ 2.5 KiB，可放片上 | 换成 `line_buffer` + `line_ready` 驱动的填充状态机 + VGA 读指针按行取 | 容量和带宽都过关；把"整帧"降级成"整行"，`line_ready` 立刻有了真实用途 |
| SDRAM 帧缓冲 | 外部 8/16 MiB | `frame_mem` 换成 SDRAM 控制器端口，2×2 复制改成读 burst | 容量最宽裕；引入了 CAS/刷新/turnaround，2×2 复制要靠 burst 连续读同一行来维持 |
| tile 缓存 | 视 nametable 大小 | 不是本模块的替代品，是补充 | 适合 CPU 侧访问 nametable，不解决整帧显示 |
| 整帧片上缓存 | 120 KiB | 无 | **在 EP4CE10 上不可行**（第 5.1 节） |

行缓冲方案的形状和现在**非常接近**，因为 `line_ready` 已经是正确的握手信号了：

```text
PPU ──pixel_valid──► 行缓冲填充器 ──line_ready──► 交给 VGA 读指针
                                          └─ 一行 256 个源像素被复制成 512 个输出像素
VGA 时序发生器（还没有）提供 hsync/vsync/de 和 640 宽的有效窗口
```

具体还需要补的东西：

1. **VGA 时序发生器**（800×525 计数器 + 96/48/640/16 段 + 场 2/33/480/10 段），输出 `hsync`/`vsync`/`de`，并在 `de` 为低时把 RGB565 输出为 0。
2. **横向填充**：行缓冲把 256 个源像素扩成 512（或 640）个输出像素；这一步仍然只是地址右移，2×2 不变。
3. **黑边**：640 = 64 + 512 + 64，用一个 `de` 窗口常量表达，不需要额外 RAM。
4. **读延迟对齐**：FPGA BRAM 是同步读，1 拍延迟；`de` 窗口要相应提前 1 拍，否则图像右移 1 像素。这类 off-by-one 在 TB 里必须用"有效窗口内第一个像素对应源列 0"这样的断言钉住。
5. **复位契约更新**：换成行缓冲后，"复位不清内容"这条仍然成立（BRAM 的性质），但"复位把读指针归零"在真实设计里可能改成"复位把 VGA 计数器归零"。

### 5.4 这个模块现在该怎么用

在换成行缓冲/SDRAM 之前，本模块的正确用法是：

- **当作行为参考模型**。它把"2 倍放大 = 地址右移"这件事表达得足够清楚，`tb_nes_video_scaler.v` 已经把调色板、2×2 复制、行/帧握手、复位语义全部钉死。后面写行缓冲版本时，可以直接拿这套断言的**期望值**（`pal_ref(pattern_index(x>>1, y>>1, pat))`）做交叉检查。
- **当作 `nes_system` 顶层的一个叶子模块**（目前还没有实例化它；`rtl/nes_core/system/nes_system_v4.v` 是当前最完整的顶层，里面没有 video scaler）。
- **不要**直接综合进 EP4CE10 的比特流。

## 6. 验证状态

`tb/video/tb_nes_video_scaler.v` 用 `$fatal` 断言覆盖：复位、64 项调色板、整帧 240×1 的行/帧握手、245,760 像素的完整读流（坐标 + 颜色 + 2×2 复制）、三帧连续、帧中复位、读指针与写口解耦、以及"输出只有 512×480 没有黑边"这条显式断言。详细清单和运行方式见 `tb/video/README.md`。

已知覆盖不到的地方（写在 TB 的 README 里，这里也记一份）：

- 全帧颜色校验只能用到 16 种颜色，因为写口 `in_pixel_index` 只有 4 位；
- 图样周期是 16，源坐标偏移 16 的错误靠颜色查不出来（靠坐标序列抓）；
- 没有任何时序断言，因为模块里没有时序发生器。
