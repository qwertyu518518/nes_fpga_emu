# 单读单写异步 FIFO（CDC）：格雷码指针如何把两个时钟域解耦

本文说明 `rtl/nes_core/peripheral/nes_cdc_fifo.v` 的接口合同、时序模型和设计取舍，并回答一个贯穿本项目的教学问题：

> 一个用 C 写的软件模拟器在两个"模块"之间传数据，只需要一个 `buffer[head++] = x; ... = buffer[tail++]`；而一个用 Verilog 写的异步 FIFO，为什么要把一半的逻辑花在"指针怎么编码"上？为什么不能直接把二进制写指针递到读时钟域里比一比？

结论：**软件里生产者和消费者共享同一根时间轴（同一个线程、同一个内存系统），硬件里两个时钟域的时间轴互不知道对方。** `nes_cdc_fifo.v` 实现的是后者：一个 **单写时钟 `wr_clk` / 单读时钟 `rd_clk`** 的环形缓冲，写入端和读出端各自维护**自己的二进制指针**（用于寻址）和**自己的格雷码指针**（用于发布给对侧）。跨域传递的永远只有格雷码指针，而且是每拍只可能翻一位的那种。

注意：本模块没有对应的"NES 真值"可引用。NES 主板上的 CPU、PPU、APU 各有自己的时钟，但任天堂没有公开过一份"跨时钟域 FIFO 规格"。所以本文里凡是讲通用 FIFO 原理的地方都标注 `[RTL 建议]`，它表达的是**工程取舍**（业界标准的 Cliff Cummings 双时钟 FIFO 结构），不是 NES 硬件规格。

---

## 1. 为什么需要异步 FIFO：两个时钟域的直接传递是错的

### 1.1 一个比特跨域，本身就有亚稳态风险

`[RTL 建议]` 假设 `wr_clk` 和 `rd_clk` 频率、相位都没有固定关系。把 `wr_bin` 的一位直接接到 `rd_clk` 域的触发器上，会发生两件事：

1. **建立/保持时间违反。** 输入数据的跳变点可能正好落在接收触发器的采样窗口里。
2. **亚稳态。** 触发器的输出可能在一小段时间内既不是 0 也不是 1，之后才随机落到某一侧。传播下去的电路在这个窗口里读到的是什么，无法保证。

单比特尚且如此，如果**一次给整条二进制指针总线**，问题会从"某一位可能错"升级成"这一次采样可能**混进旧值和新值**"——也就是下面 1.2 说的撕裂。

### 1.2 多比特直接跨域会撕裂

`[RTL 建议]` 二进制指针递增时可能翻好几位。比如 3 位二进制从 `011` 到 `100`，三位一起变。如果接收域正好在这次跳变中间采样，采样结果可能是 `000`、`111` 或其它任何一种中间组合——这个值**从来没有在源域存在过**。一个从未存在过的指针会让满/空判据得出错误结论，进而丢数据或重复读。

本模块的答案分两层：

- **发布层**：跨域只传**格雷码**指针，每拍最多翻一位，从根上消灭撕裂（第 2 节）。
- **接收层**：格雷码在进入对侧异步逻辑之前，先过一个**两级触发器同步器**（`rd_gray_sync1/sync2`、`wr_gray_sync1/sync2`），把亚稳态压到"最多错一拍、错也只错一位"的范围内。

## 2. 格雷码为什么安全：一位一变，加上"寻址/发布"分工

### 2.1 每次只翻一位

`[RTL 建议]` 格雷码的定义是相邻两个码字只有一位不同。模块里指针是这样算的：

```verilog
wr_gray_next = (wr_bin + PTR_ONE) ^ ((wr_bin + PTR_ONE) >> 1);
```

也就是对**递增值**做标准的二进制转格雷（`g = b ^ (b >> 1)`）。因为是相邻递增，所以新旧格雷码恰好差一位。跨域采样时，接收端看到的那一位要么还是旧值、要么已经是新值，**不存在介于两者之间的第三种组合**。这就是它能安全跨域的全部理由。

### 2.2 二进制指针负责寻址，格雷指针负责发布

模块给每个端口维护了两份指针，职责是分开的：

| 指针 | 宽度 | 用途 | 是否跨域 |
| --- | --- | --- | --- |
| `wr_bin` / `rd_bin` | `PTR_WIDTH` | 取低位 `[ADDR_WIDTH-1:0]` 去索引 `mem` | 否，只在本地域 |
| `wr_gray` / `rd_gray` | `PTR_WIDTH` | 发布给对侧同步器，参与满/空比较 | 是 |

为什么不能只用格雷码寻址？因为格雷码不是顺序码，`mem[gray]` 不落在正确的物理地址上；为什么不能只发布二进制码？因为它会撕裂。**所以两者都要**，二进制管本地地址，格雷码管跨域比较。`[源码观察]` 文件头注释就是这么描述的："a binary pointer that addresses the storage array and a Gray pointer that is published to the other domain"。

指针为什么是 `PTR_WIDTH = ADDR_WIDTH + 1`？多出来的最高位是**回绕标志位**。深度是 `2**ADDR_WIDTH`，指针在 `0 .. 2**(ADDR_WIDTH+1)-1` 里循环，多出的那一位让满和空能够区分（见第 3 节）。

## 3. 满 / 空判据逐位解释

两条判据在文件里是：

```verilog
wr_gray_at_full = {~rd_gray_sync2[PTR_WIDTH-1:PTR_WIDTH-2], rd_gray_sync2[PTR_WIDTH-3:0]};
wr_full_next    = (wr_gray_next == wr_gray_at_full);
rd_empty_next   = (rd_gray_next == wr_gray_sync2);
```

### 3.1 空：整字相等

读指针和"同步过来的写指针"**完全相等**就代表没有数据：读者已经追上了写者。比较的是 `rd_gray_next`（读者**下一拍**将处于的位置）与 `wr_gray_sync2`（写者已经落地的位置）。用 `rd_gray_next` 而不是 `rd_gray`，意味着"这一拍读完之后是否立刻变空"在一个沿上就决定好了，不需要额外等待。

### 3.2 满：反转最高两位

`wr_full_next` 拿写者的下一个格雷码与 `wr_gray_at_full` 比。`wr_gray_at_full` 是把同步过来的读指针 `rd_gray_sync2` 的**最高两位取反、其余位照抄**。这等价于二进制世界里"写指针恰好比读指针超前整整一圈（`2**ADDR_WIDTH` 项）"。

为什么是"最高两位"而不是"最高一位"？因为指针比地址多一位（`PTR_WIDTH = ADDR_WIDTH+1`）。在格雷码里，一个回绕（跨越半圈）对应最高两位一起翻转的组合。Cliff Cummings 的经典写法就是反转最高两位，本模块照抄了这个签名。任何一位没有严格对齐（比如同步器采样到的是上一圈的旧值），最高两位不会同时呈现这个组合，满标志也就不会误判。

### 3.3 这两条判据只在"格雷码每拍翻一位"的前提下成立

如果指针不是格雷码，同步器采到撕裂值，这两条等式就会命中一个本不存在的状态。判据的正确性完全建立在第 2 节的性质上。

## 4. 存储阵列为什么长这样

### 4.1 每 bit 一对触发器

`[源码观察]` 文件头注释写得很直白："Every bit of the array is a pair of flip-flops"。存储体是 `reg [DATA_WIDTH-1:0] mem [0:DEPTH-1]`，写侧在 `wr_clk` 沿写 `mem[wr_bin[...]]`，读侧在 `rd_clk` 沿把 `mem[rd_bin[...]]` 打进 `rd_data`。同一块阵列被两个时钟沿分别写和读，本质是一块**双时钟简单双端口 RAM**（一写口、一读口）。

`[RTL 建议]` 这种"每 bit 一对触发器"在综合器眼里通常会被推断成 Block RAM，但**它并不保证**：`[源码观察]` `rtl/platform/zynq/nes_zynq_top.v` 的音频例化注释里明确记录过代价——默认 `ADDR_WIDTH=10` 会让 1024×32 位阵列吃掉约 65536 个触发器，直接把 xc7z020 的放置器撑爆，所以真实例化时改用了 `ADDR_WIDTH=6`。这条记录说明**深度选择会直接决定它落地成寄存器还是 BRAM**，不是一个纯参数问题。

### 4.2 `rd_data` 为什么不是组合读

读出是寄存器输出：

```verilog
if (rd_en && !rd_empty)
    rd_data <= mem[rd_bin[ADDR_WIDTH-1:0]];
```

不是 `assign rd_data = mem[rd_bin]`。原因有二：`[RTL 建议]` 其一，组合读会让 `rd_data` 在 `rd_bin` 变化的瞬间抖动，而 `rd_bin` 又跨了一次时钟沿，读者需要一个稳定的样点；其二，寄存输出让"读完这一项"这个语义有一拍的落点，testbench 才能断言"`rd_empty` 为 1 时 `rd_data` 不许变"。`[源码观察]` `tb_nes_cdc_fifo.v` 里的 `RD_HOLD` 检查正是钉住这一点的：`rd_empty` 为高的那一拍，`rd_data` 必须保持上一拍的值。

### 4.3 阵列为什么不带复位

两个 `always` 块只复位指针和标志，从不去清 `mem`。因为**一个存储槽在被写过之前是没有意义的**，而"有没有被写过"这件事正好由两个指针的满/空判据保证：读者绝不会读一个从未写过的槽（空判据拦住），写者也绝不会覆盖一个还没读走的槽（满判据拦住）。给一个 65536 触发器的大阵列加异步复位只会白白浪费复位布线资源。`[源码观察]` 文件头注释："an entry only becomes meaningful once it has been written, which is exactly what the two pointer flags guarantee"。

## 5. 握手语义：延迟的对侧指针

### 5.1 提交条件

- 写：`wr_en && !wr_full` 才真正提交，`wr_bin`/`wr_gray` 前进，`mem` 写入。
- 读：`rd_en && !rd_empty` 才真正提交，`rd_bin`/`rd_gray` 前进，`rd_data` 更新。

`wr_en` 在满时拉高、`rd_en` 在空时拉高，都会被**忽略**：指针不动、什么都不发生。这一点 `[源码观察]` `tb_nes_cdc_fifo.v` 的 phase 1b 和 phase 2 专门断言过——满时写一个 `BAD_VALUE`，模型不记录它，随后 drain 出来的项里没有它；空时读两次，`rd_empty` 和 `wr_full` 都不变。

### 5.2 写侧看到的是延迟的读指针

`wr_full` 判据里用的是 `rd_gray_sync2`——读指针**穿过两级写域同步器之后**的副本。这意味着写侧看到的读进度永远是滞后的：

- 一项数据被读走之后，读指针前进；它要经过 `rd_gray_sync1 -> rd_gray_sync2` 两个 `wr_clk` 沿才抵达 `wr_full` 的比较逻辑。
- 在这几拍里，`wr_full` 可能仍然保持为 1，即使读者其实已经腾出了空间。

读侧的 `rd_empty` 同理：写者写入第一项之后，写指针要穿过两级 `rd_clk` 同步器，`rd_empty` 才可能落下来。**满标志滞后几个读时钟、空标志滞后几个写时钟，是这套结构的固有性质，不是缺陷。** 生产者看 `wr_full` 决定"这一拍还塞不塞得进"是安全的；它看的是稍旧的状态，最坏情况只是这一拍多等一拍、而不是覆盖数据。

## 6. 复位：两个域各自独立

### 6.1 谁清什么

| 复位 | 时钟域 | 清零对象 |
| --- | --- | --- |
| `wr_reset` | `wr_clk` | `wr_bin`、`wr_gray`、`wr_full`、`rd_gray_sync1/sync2` |
| `rd_reset` | `rd_clk` | `rd_bin`、`rd_gray`、`rd_data`、`rd_empty`、`wr_gray_sync1/sync2` |

注意每个复位**顺手也清掉自己域里的那两个同步器**——因为同步器物理上就住在本域，只能由本域的复位来清。

### 6.2 为什么相互独立、不同步进对侧

两个复位**从不被同步到对侧域**去。原因：这是两个真正独立的时钟域，任何"把 A 域的复位信号同步到 B 域"的做法都要再引入一组同步器，还得面对复位释放时刻的对齐问题。`[源码观察]` 文件头注释直接点明：复位期间跨域指针可能不一致，复位释放后"a few entries may be discarded or replayed before the two pointers line up again"（会有若干项被丢弃或重放，直到两侧指针重新对齐）。

### 6.3 为什么要一起复位

正因为单独复位一侧会造成指针不一致，**两个域应当同时复位**。`[源码观察]` 文件末尾也是这么写的："Both ends should be reset together."。testbench 的 phase 4 特意**各自单独**复位一次来证明：单独复位不会挂死、标志都能恢复，但中途会丢/重放数据；最后 phase 4i 用一次联合复位加 32 项往返，确认重新对齐后行为完全干净。

## 7. 参数

```verilog
module nes_cdc_fifo #(
    parameter DATA_WIDTH = 32,
    parameter ADDR_WIDTH = 10
) (...);
```

| 参数 | 默认 | 含义与约束 |
| --- | --- | --- |
| `DATA_WIDTH` | 32 | 每项位宽。同时决定 `mem` 的列宽和 `rd_data` 的宽度。 |
| `ADDR_WIDTH` | 10 | 深度指数，深度 `= 2**ADDR_WIDTH` 项。约束 `ADDR_WIDTH >= 2`，所以最小深度是 4；默认 10 即 1024 项。 |

派生常量：`DEPTH = 1 << ADDR_WIDTH`，`PTR_WIDTH = ADDR_WIDTH + 1`，`PTR_ONE` 是 `PTR_WIDTH` 位里的 1。`ADDR_WIDTH >= 2` 的要求来自满判据取"最高两位"——如果只有一位地址位、指针仅两位，"最高两位"的格雷回绕签名就退化了，所以模块不接受过浅的深度。

## 8. 接口合同

| 信号 | 方向 | 合同 |
| --- | --- | --- |
| `wr_clk` | in | 写侧时钟。写指针、满标志、读指针同步器都踩这个沿。 |
| `wr_reset` | in | 写侧高有效**异步**复位。只影响 `wr_clk` 域。 |
| `wr_en` | in | 写请求。仅在 `!wr_full` 时提交；满时被忽略。 |
| `wr_data` | in | 写入数据，`DATA_WIDTH` 位。仅在提交那拍被写进 `mem`。 |
| `wr_full` | out | 满标志（寄存器）。用同步过来的读指针判定；滞后若干 `wr_clk` 拍。初值 0。 |
| `rd_clk` | in | 读侧时钟。读指针、空标志、写指针同步器都踩这个沿。 |
| `rd_reset` | in | 读侧高有效**异步**复位。只影响 `rd_clk` 域。 |
| `rd_en` | in | 读请求。仅在 `!rd_empty` 时提交；空时被忽略。 |
| `rd_data` | out | 读出数据，`DATA_WIDTH` 位。**寄存输出**，`rd_empty` 为高时保持上一拍值。 |
| `rd_empty` | out | 空标志（寄存器）。复位后初值 1。 |

内部同步器寄存器 `rd_gray_sync1/sync2`、`wr_gray_sync1/sync2` 都带 `(* ASYNC_REG = "TRUE" *)` 综合属性——`[RTL 建议]` 它通知工具"这两个触发器是一级同步器，请摆在一起、不要拆开优化或重定时"。它们不对外暴露。

## 9. 周期账 / 水位

以 testbench 实际使用的时钟为例：`wr_clk` 周期 10 ns（`#5` 翻转），`rd_clk` 周期 14 ns（`#7` 翻转）——两个周期互质，相位和比值一直漂移，跨域每一拍都在被不同相位组合考验。

`[RTL 建议]` 水位（占用项数）= 写指针与读指针之差，模 `2*DEPTH`：

| 事件 | 写侧可见的 `wr_full` | 读侧可见的 `rd_empty` |
| --- | --- | --- |
| 写入一项 | 若差到 `DEPTH` 则置 1 | 需等该项穿过两级 `rd_clk` 同步器才落 0 |
| 读走一项 | 需等读指针穿过两级 `wr_clk` 同步器才落 0 | 若差归 0 则置 1 |

因此**最坏情况下 `wr_full` 会比真实占用水位晚 2 个 `wr_clk` 拍才落、`rd_empty` 会比真实非空晚 2 个 `rd_clk` 拍才落**。这不是丢数据的窗口：在这段滞后里写者只是被保守地挡住（少写一拍），读者也只是被保守地挡住（少读一拍）。这个保守性是这套结构的正确性来源——**永远宁可多等一拍，也不让指针越过对侧还没看到的位置**。

## 10. 明确未实现 / 未建模

- **没有 almost-full / almost-empty。** 只有精确的满和空两个标志，没有"快满/快空"预警，生产者无法提前几项减速。
- **没有可编程阈值。** 就两个标志位，没有把水位设成某个用户指定的项数。
- **没有 `wr_rst_busy` / `rd_rst_busy`。** 不像 Xilinx FIFO IP 那样给一个"复位还没结束、先别写"的握手；本模块靠"两级同步器会在几拍内对齐"自行恢复。
- **阵列不参与复位。** 复位后 `rd_data` 被清成 0，但 `mem` 里的旧内容仍在；只有指针和标志的复位保证这些旧内容不会被读到。
- **CDC 属性只是综合提示。** `ASYNC_REG` 依赖工具识别；模块本身不产生任何时序约束文件，也不做跨域检查。
- **与 `nes_system_v*` 系列 System 顶层和 EP4CE10 平台顶层无关。** `rtl/nes_core/system/` 下的任何 `nes_system_v0..v6` 都没有例化它，`rtl/platform/ep4ce10/nes_ep4ce10_top.v`（本项目的目标板）也没有。
- **它确实被间接例化了，仅在 Zynq 平台。** `[源码观察]` 唯一的使用点是 `rtl/platform/zynq/nes_zynq_top.v` -> `rtl/nes_core/peripheral/nes_audio_i2s.v` -> `nes_cdc_fifo`（实例名 `u_fifo`），用于把音频写侧的 `core_clk` 域搬到 I2S 的 `lcd_clk` 读侧；那里为了省触发器把 `ADDR_WIDTH` 改成 6。这与"没有任何平台顶层例化"的常见假设不符，以这条为准。
- **Zynq 上确实有时序约束证据。** `[源码观察]` `rtl/platform/zynq/nes_zynq_top.xdc` 里对 `u_audio_i2s/u_fifo/wr_gray_reg -> wr_gray_sync1_reg`、`rd_gray_reg -> rd_gray_sync1_reg`、`mem_reg -> rd_data_reg` 三组路径下了 `set_max_delay -datapath_only 40.000`，而不是 `set_false_path`——目的是保住同步器两级之间的物理邻近，同时去掉无意义的建立检查。EP4CE10 平台没有对应约束。
- **testbench 未覆盖**：没有测 `ADDR_WIDTH=2`（最小深度 4）的边界；没有测极端时钟比（如读侧比写侧慢一个数量级）；`rd_clk`/`wr_clk` 只在 10 ns vs 14 ns 这一组固定相位关系下跑（`[源码观察]` `tb_nes_cdc_fifo.v`）；phase 3 的随机激励用固定 `$random`，不是可控种子的定向用例。
- **未与真实生产者/消费者端到端联通**：除音频那条通路外，没有用本 FIFO 串起其它 NES 子系统；本模块不解析任何 NES 地址或时序语义。
