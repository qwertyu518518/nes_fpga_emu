# 验证计划

## 1. 验证目标

验证分为两个相互独立的问题：

1. 功能结果是否正确：寄存器、RAM、栈、内存结果和中断跳转是否符合预期。
2. 可观察时序是否正确：每次 `bus_fire` 的地址、方向、数据、dummy、RMW、ready/hold 和中断序列是否符合合同；对 PPU/System 还包括 dot/scanline 计数、vblank/NMI 窗口、`ce` 分频相位和帧周期；对 CPU 总线、DMA、mapper、APU、controller、iNES 解析、video scaler、VGA 行缓冲、VGA 时序和平台顶层还包括等待拍数、ack 握手、bank/串行寄存器转移、串行读位序、行边界握手与像素流位置的固定时序账。

“画面能显示”“声音能听见”或“最终 PC 正确”不能替代总线 trace。固定 C 模型可以帮助发现差异，但 C 模型本身不是 NES 行为权威。所有 testbench 都在固定输入上自建内存或镜像，不加载外部 ROM，所以它们能证明的是 RTL/TB 内部一致性，而不是任何真实 ROM 的行为。

`g_chr_external` 里**同时**例化了 `nes_chr_fetch_unit`（背景）与 `nes_sprite_chr_fetch`（精灵），**少列任何一个都会在 elaboration 阶段报 `Unknown module type`**，所以这条目标的五个文件必须全部显式列出；成功时打印 `A1 total compared pixels=921600 ...`、`A3 `sprite-fetch-tb`（`Top = 'tb_nes_sprite_chr_fetch'`、`Standard = '2012'`、跑 `vvp`）的源文件列表都只有 `nes_sprite_chr_fetch.v`**（`+ tb\ppu\tb_nes_sprite_chr_fetch.v`）——`nes_sprite_chr_fetch` 同样**没有任何子模块**、不例化任何东西，所以两个精灵目标自己的源文件列表只有一个 RTL 文件；**但 `nes_ppu2c02` 现在已经在 `g_chr_external` 里例化它了**，所以 `nes_sprite_chr_fetch.v` **进了** `ppu-ext-chr-tb` 的源文件列表（该目标现在是**五条**：PPU 集 + `nes_chr_fetch_unit.v` + `nes_sprite_chr_fetch.v` + TB），少列它会在 elaboration 阶段报 `Unknown module type: nes_sprite_chr_fetch`；成功时打印 `A3 all 16 equal the spec byte-address sequence: ...` 与 `PASS nes_sprite_chr_fetch`。`-Mode ppu` 因此从 8 个目标变成 **10 个**（4 编译 + 6 仿真）。**`chr-feasibility-tb` 不是等价性测试**，性质见第 2 节的“CHR 取数可行性测量 TB”一行与 7.2/7.1 对应条目；`ppu-ext-chr-tb` **是**等价性测试但**只覆盖背景**。`chr-fetch-tb` 与 `chr-feasibility-tb` 是两回事：前者断言取数状态机**在 33 个 tile 的最坏行上**行为正确，后者只测量 dot 预算；`ppu-ext-chr-tb` 是第三回事：它断言**整个 PPU 在两条 CHR 路径上渲染出相同像素**。

`cdc-fifo-tb` 是 34 个 testbench 目标里**唯一**用 `-g2001` 编译的：`tb/peripheral/tb_nes_cdc_fifo.v` 与它的 DUT 都是纯 Verilog-2001（只用 `$random`，没有 `$fatal`），判定靠 TB 自己的 `tb_live` 标志加 `$finish`，打印 `PASS nes_cdc_fifo` 后正常结束。`chr-fetch-tb`、`sd-spi-cmd-tb`、`ppu-ext-chr-tb` 和 `sprite-fetch-tb` 都用 `$fatal` 判定，因此按既有先例用 `-g2012`；它们对应的 compile-only 目标 `chr-fetch-core`、`sd-spi-cmd-core` 与 `sprite-fetch-core` 用 `-g2001`。

`iverilog` 不会自动解析依赖，所以每个目标的源文件列表都必须写全：PPU 集带 `nes_ppu_sprite.v`，OAM DMA 单列一组，APU 集带 5 个通道/查找表子模块，mapper 集带 5 个子模块，bus 目标带 DMA 读端口所在的 `nes_cpu_bus.v`，system v4 在 v3 的列表上再加 `nes_controller.v`，system v5 在 v4 的列表上再加整个 mapper 集（6 个文件），三个平台目标在 v4 的列表上再加平台集（3 个文件）和 `nes_line_buffer_vga.v`、`nes_vga_timing.v`。少任何一个文件，缺的是该文件的实例而不是报清晰的错。**`ppu-ext-chr-tb` 的五个文件必须全部显式列出**：PPU 集的两个文件加上 `nes_chr_fetch_unit.v` 与 `nes_sprite_chr_fetch.v`（`EXTERNAL_CHR=1` 的 `nes_ppu2c02` 在 `g_chr_external` 里同时例化了这两个取数单元）加上 TB 本身。I2S 组装层两个目标必须同时带上 `nes_cdc_fifo.v` + `nes_i2s_shifter.v` + `nes_audio_i2s.v` 三个文件，因为 `nes_audio_i2s` 例化了前两个模块（`iverilog` 不做依赖解析，只给 `nes_audio_i2s.v` 一个文件会在 elaboration 阶段报 `Unknown module type: nes_cdc_fifo / nes_i2s_shifter`）。行缓冲目标只需要它自己那一个 RTL 文件（没有子模块），`tb_nes_line_buffer_vga.v` 在同一文件里例化两个参数实例，不需要额外的 RTL；CHR 取数目标同样只需要 `nes_chr_fetch_unit.v`、精灵 CHR 预取目标同样只需要 `nes_sprite_chr_fetch.v`（两个单元都没有子模块，TB 各自只例化一个实例）、SPI 命令帧目标同样只需要 `sd_spi_cmd.v`（它也没有子模块，两个参数的 `CLK_HZ`/`SPI_HZ` 都由 TB 覆盖实例传入）、VGA 时序目标同理只需要 `nes_vga_timing.v`（纯计数器，不实例化 `nes_video_scaler`、不拥有 frame buffer），`tb_nes_vga_timing.v` 也不例化其它 DUT。`platform-core` 同样必须写全依赖：`nes_ep4ce10_top` 实例化了 `nes_system_v4`、`nes_line_buffer_vga` 和 `nes_vga_timing`，只给平台集两个文件会在 elaboration 阶段报 `Unknown module type`。`qsf-if-core` 的顶层 `nes_ep4ce10_qsf_if` 是 `nes_ep4ce10_top` 的引脚封装层（把 5/6/5 位 RGB 拼成 16 位 `vga_rgb`、用 `clk_vga` 自由运行计数器驱动 4 个 `led`，并实例化平台顶层），所以它和 `platform-core`/`platform-tb` 用**同一条**完整源文件列表；只给平台集三个文件一样会报 `Unknown module type: nes_system_v4 / nes_line_buffer_vga / nes_vga_timing`。平台集把 `nes_ep4ce10_qsf_if.v` 列进去不会影响 `platform-core`/`platform-tb`：这两个目标用 `-s` 指定顶层，`iverilog` 只 elaborate 指定的那个 root，多出来的 root 只被解析不展开。

## 4. 分阶段通过/失败判据

L0–L2 的判据是 CPU 专用的。PPU、APU、CPU 总线、mapper、controller、iNES 解析、video scaler、VGA 行缓冲、VGA 时序、平台顶层、QSF 引脚封装层、WM8978 外设、SD/eMMC SPI 命令帧发送器、CHR 取数单元、异步 CDC FIFO 和 System 的等价判据记录在各自 `tb/*/README.md` 的“断言覆盖”和“变异验证”章节（`tb/platform/` 和 `tb/peripheral/` 还没有 README，其断言清单在 TB 文件头），遵循同一条上限：只证明 RTL/TB 内部一致性，不产生综合、时序或板级证据。新增判据层时必须同时更新第 7.2 节的上限。

### L0：工具和 elaboration

**通过条件：**

- 脚本找到指定的 `iverilog.exe` 和同目录 `vvp.exe`。
- 50 个目标引用的全部 RTL 源文件和 34 个 testbench 源文件存在（缺少任何一个时脚本在编译前就报错并退出 1）。
- 十六个 core 目标用 `-g2001` 编译/elaborate 返回 0。
- 33 个 testbench 目标用 `-g2012` 编译并由 `vvp` 跑完返回 0；`cdc-fifo-tb` 用 `-g2001` 编译并由 `vvp` 跑完返回 0。
- `.\tools\sim_all.ps1 -Mode all` 汇总表全部为 `PASS`，脚本退出码 0。

**失败条件：**

- 工具路径不存在、权限不足或版本不兼容。
- Verilog 语法、模块端口、top 名称或 elaboration 失败。
- 输出文件无法写入临时目录。
- 任何目标 FAIL 时脚本退出码非 0。

### L1：CPU 集成行为

**通过条件：**

- reset 的 5 个 dummy 地址和 `$FFFC/$FFFD` 顺序正确。
- reset 后 `SP=$FD`、P bit 5 为 1，程序最终寄存器、标志和内存 marker 正确。
- 立即数、零页、绝对、索引、间接、ADC/SBC、比较、分支、转移、RMW、JMP/JSR/RTS、BRK/RTI、NMI/IRQ 场景通过。
- 注入的 `bus_ready` stall 被观察到，且 stall/hold 不改变等待中的输出。
- testbench 正常打印 `PASS` 并以 0 结束。

**失败条件：**

- 任何 `$fatal`、超时、非法 opcode 误报、最终 PC/A/X/Y/SP/P 不符。
- 栈 push/pull 的绝对地址或 SP 更新不符合合同。
- NMI/IRQ 向量、push PC、B 位或 P bit 5 不符。

### L2：逐事务 bus conformance

**通过条件：**

- 每个场景的 reset 前缀和指令事务索引与固定预期一致。
- indexed read 的 dummy 地址、页交叉处理和 RMW 旧值/新值写入顺序正确。
- `STA` 只写最终地址，dummy 地址不被修改。
- `JMP ($xxFF)`、分支、RTS dummy、IRQ/NMI/BRK push 和 hijack 的地址序列正确。
- `$01xx` 每个事务都满足绝对栈地址规则。
- `bus_ready=0` 或 `bus_hold=1` 时 `bus_addr`、`bus_we`、`bus_dout` 不漂移。
- 所有非法 opcode 场景在 fetch 后停止发事务，`dbg_illegal` 置位且架构状态不变。

**失败条件：**

- 只比较最终内存而忽略 dummy、方向或地址。
- 等待/保持期间输出改变。
- 任意栈槽、向量顺序或 RMW 写次数不符。
- 把当前已知微周期差异误报成新的未分类失败；这类差异应先与 [`cpu-contract.md`](cpu-contract.md) 对照。

### L3：golden model 差分

C golden model 是下一层证据，不是当前仓库已完成项。加入时按以下步骤：

1. 固定 c6502 或选定 C 模型的提交、编译选项、输入 ROM、reset 长度和中断刺激。
2. 定义稳定的规范化 trace，例如 `cycle, pc, addr, rw, wdata, rdata, state`，明确是否包含 reset 周期和等待周期。
3. 让 C 模型和 RTL 使用同一组初始寄存器、向量、RAM/ROM 内容和 NMI/IRQ 到达点。
4. 先比较每个 `bus_fire` 的地址、方向和数据，再比较 PC、A、X、Y、SP、P 和非法状态。
5. 把差异分类为：仅最终数据、周期不同、dummy 不同、同周期优先级不同、C 模型近似、硬件资料不足或 RTL 缺陷。
6. 不用“与 C 不同”直接判 RTL 失败；先判断预期是否来自 NESdev/测试 ROM。固定 C 只用于发现共同假设和回归变化。

差分通过的最低条件是：每个差异都有分类和解释；关键官方指令、栈、向量和 dummy 序列没有未解释差异；固定 seed、输入和工具版本可重现。

### L4：test ROM 回归

test ROM 接入也是计划项，不是当前证据。推荐分层加入：

1. 选择小型、许可清晰、结果可判定的 CPU/总线测试 ROM。
2. 写一个只负责加载/映射 PRG、设置 reset vector 和 mapper 初始状态的仿真 loader；不要在 CPU FSM 中加入文件解析。
3. 对 NROM 先验证 `$8000-$FFFF` 固定/镜像窗口、2 KiB RAM 镜像和 reset vector。
4. 再加入 PPU vblank/NMI、OAM DMA 和 APU IRQ；每次只增加一个可观察边界。
5. 记录 ROM 文件哈希、mapper、制式、预期结果、运行 cycle 数和失败的首个差异。

通过条件是测试 ROM 自己报告通过，并且 RTL trace 没有违反地址、owner、ready、栈和中断合同。失败条件包括 loader 边界错误、mapper 初始窗口错误、结果 marker 错误或出现未解释的总线差异。

### L5：Quartus 和 EP4CE10 平台

只有 core 行为回归稳定后才进入此层。通过条件至少包括：

- 目标器件、封装、速度等级和顶层端口与 QSF 一致。
- PLL 输出、generated clock、SDC 和 TimeQuest slack 报告完整。
- BRAM/FIFO 使用量、IO bank、未约束路径和外部时序满足目标。
- VGA、TF、SDRAM、WM8978 和 GPIO 的板级电气/时序分别有测量证据。

当前**有**一个平台顶层 `rtl/platform/ep4ce10/nes_ep4ce10_top.v` 和一个引脚封装层 `rtl/platform/ep4ce10/nes_ep4ce10_qsf_if.v`（后者把 5/6/5 位 RGB 拼成 16 位 `vga_rgb`、用 `clk_vga` 自由运行计数器驱动 4 个 `led`、`beep` 绑 0，并例化平台顶层；它**不含任何约束语法**），也**有**一份 Quartus 工程骨架：`quartus/op_fpga_emu.qpf`、`quartus/op_fpga_emu.qsf`、`quartus/op_fpga_emu.sdc` 三个文件都已存在（实测计数见 `quartus/README.md` 第 0.1 节，文件级说明见 `quartus/README.md`）。但**骨架不是结果**：这三个文件**从未在 Quartus 中打开或编译过**（本机没有安装 Quartus），所以本层**没有任何综合、Fit、STA、引脚分配或上板证据**。骨架内部仍有四类缺口——(1) `.qsf` 里 `set_location_assignment` / `set_io_assignment` / `PIN_LOCATION` 生效条数**各为 0**，即**一个引脚都没分配**；(2) `.sdc` 里生效的 `create_generated_clock` **0 条**、`derive_pll_clocks` **0 条**，即**altpll 尚未生成**，`clk_ntsc`/`clk_vga` 现在只是自由驱动的输入端口引脚，状态 A → B 的改写清单在 `.sdc` 第 6 节的 `TODO(PLL)`，步骤与判据在 `docs/hardware/12-ntsc-clock-and-pll.md` 第 6 节；(3) `.qpf` 只是占位，`.qip` 与 `.sdf` 不存在；(4) `nes_ep4ce10_pll_stub.v` 仍只是把 `clk_in` 同时送到 `clk_ntsc`/`clk_vga` 的占位模块，真实器件上必须换成 MegaWizard 生成的 altpll IP。因此 `nes_ep4ce10_top` 的 3 个时钟、1 个 `reset_n`、4 个按键、6 个 VGA 输出和 2 个音频输出以及 `nes_ep4ce10_qsf_if` 的 `sys_clk`/`sys_rst_n`/`key[3:0]`/`vga_hs`/`vga_vs`/`vga_rgb[15:0]`/`led[3:0]`/`beep` 都没有引脚分配，generated clock、输入/输出延迟与 IO bank/电平约束也全部缺失。`nes_system_v0`/`v5` 仍只是仿真用顶层，没有引脚、时钟、存储器和 IO 约束；v5 里的 `buttons1`/`buttons2` 是与 `clk` 同步的常量端口（平台顶层才把它们变成同步 + 消抖后的异步输入）。v5 多了 128 KiB 的 `prg_rom` 数组和五个 mapper 子模块（`MAPPER_SELECT` 是 elaboration 期参数），而平台顶层用 `nes_system_v4` + 16 KiB `PRG_SIZE_BYTES`，这两项的 M9K 占用同样**没有** Fitter 数字。`nes_line_buffer_vga` 是双时钟模块（`wr_clk`/`rd_clk`），它的两级 toggle 同步器和顶层的 `clk_sys → clk_ntsc` 两级按键同步器在 Icarus 里都是零延迟数字行为，没有任何亚稳态/MTBF 或综合后的 CDC 报告。因此此层状态是未开始，而不是失败或通过。

## 6. 完成定义

一个阶段完成必须能回答：

- 预期来自哪一类权威来源。
- 哪个 cycle、地址、状态或资源指标首先不同。
- 差异是功能、dummy、等待、DMA、CDC、工具近似还是已知合同限制。
- 结果是否在固定工具、输入和板卡版本上可重现。
- 下一项验证能否独立发现该结果，而不是依赖截图或最终画面。
