# 外部 CHR 的 `$2007` 写通路：已实现并有端到端证据

本文记录 `nes_ppu2c02` 的 `g_chr_external` 分支里**`$2007` 对 CHR 的写通路**（提交 `5cc36e7`、`576cc74`）。它是一篇**教学 + 合同**文档：解释地址从哪来、strobe 为什么必须是组合的、共享地址总线上写与读怎么仲裁、以及哪些边界仍然不能宣称。模块层面的背景/精灵取数叙事见 [`docs/modules/ppu-external-chr.md`](modules/ppu-external-chr.md)，顶层接线与地址合同见 [`docs/modules/system-v6.md`](modules/system-v6.md)，断言清单与固定输出见 [`tb/system/README.md`](../tb/system/README.md)。

**先说结论**：`$2007` 写到 `< $2000` 的写周期现在会变成外部 CHR 总线上的一次**恰好 1 `clk` 宽**的 strobe，地址是**自增前**的 `v_addr`，数据是 `reg_din`；`nes_system_v6` 上它被 `nes_mapper` 的 `chr_ram_we` 门控，**96 个写拍、0 翻译错**，并由哨兵非空洞检查、自验证对、CHR-RAM/CHR-ROM 忽略对与 MMC3 bank 限定写四组证据交叉锁定。**但**写通了不等于整条外部 CHR 通路闭合：`$2007` **读** CHR 的回读路径已经在**后一轮**补上并有端到端证据（读臂与 `chr_req` 的仲裁见 §4，读通路的合同与不能宣称的部分见 §8.1 与 [`docs/modules/ppu-external-chr.md`](modules/ppu-external-chr.md) 的读通路一节）；而读臂与取数、写与取数在共享地址总线上**各有**一条已量化、**未修**的碰撞隐患（读：396 个读臂里 **107** 个撞上在飞的取数拍；写：96 个写拍里 **22** 个），片上**没有任何 CHR 存储**，仓库里也**没有综合证据**。

`nes_ppu2c02.v:813-816` 是整条通路的全部内容（写通路落地那一轮结束时是 `:712-715`）：

```verilog
assign chr_waddr = (v_addr < 15'h2000) ? v_addr[13:0] : 14'h0000;
assign chr_we    = !reset && reg_cs && reg_we && (reg_addr == 3'd7)
                   && (v_addr < 15'h2000);
assign chr_wdata = reg_din;
```

三个信号里只有 `chr_we` 是 strobe，另外两个是"strobe 为高时必须同时正确"的伴随信号。

## 2. 为什么地址是**自增前**的 `v_addr`

`$2007` 写 CHR 的地址就是 PPU 的 `v` 寄存器当前值——真机上 `$2006` 两次写入装 `v`，`$2007` 读写都作用在它上面，**读写用同一个寄存器、写完自增**。所以 `chr_waddr` 直接取 `v_addr` 没有任何"加/减"成分，这一点值得强调是因为它**不是**取数通路的地址：

- 取数侧（背景 / 精灵）发的 `chr_addr` 是**渲染流水自己算出来的** tile 地址窗口起点（`b_k = 8k - fine_x`，见 `ppu-external-chr.md` 11.1.2），与 `v_addr` 无关。
- 写侧用的 `v_addr` 是 **CPU 通过 `$2006` 编程的地址**。两者在 `v_addr` 上没有耦合，在 `chr_addr` 上也没有耦合。

**为什么必须取自增前的那一拍。** `nes_ppu2c02` 里 `v_addr` 的自增发生在 `if (ce)` 里的寄存器读/写 always 块中（`:648` 那类 `v_addr <= increment_v(v_addr);`；写通路落地那一轮结束时是 `:552`）。`chr_we` 是**组合**的（下一节），所以在同一个 `posedge` 沿上：组合逻辑看到的 `v_addr` 是**旧值**（自增还没发生），而寄存器沿会把新值写进去。这正是硬件顺序想要的：**写必须落在 CPU 指定的那一个字节上，而不是它的后继**。如果把地址改成自增后的值，`$2006 = $0000` + `$2007 = $AA` 会写进 `$0001`；T0-1 那条每写拍比对 `chr_waddr == u_ppu.v_addr`（自增前）的断言就是为了钉死这一条。

### 2.1 `v_addr[12:0]` 的推导，和 `PPUCTRL[4]` / `[5]` 为什么无关

```verilog
assign chr_waddr = (v_addr < 15'h2000) ? v_addr[13:0] : 14'h0000;
```

- **判据用 15 bit 的 `v_addr < 15'h2000`，不是 14 bit。** 因为 `v_addr` 是 15 bit（bit 14 是 nametable 选，bit 13 在本仓库里恒 0），用 14 bit 比会漏掉 bit 14，使 `$2000`（nametable 0）也算成 CHR。判据成立时 `v_addr[14:13] == 0`，所以 `v_addr[13:0]` 就是完整的地址，`chr_waddr[13]` **结构上恒为 0**。
- **因此本地 CHR 窗口是 8 KiB / 13 bit 有效，pattern-table 选择落在 bit 12。** 这和读通路是同一条约定：`bg_tile_base` 是 13 bit、精灵 `s_pat_addr` 是 13 bit，本地 `chr_addr[13]` 声明了但恒 0（`system-v6` 的 P0-3 实测 **21,002** 次请求里置位 0 次——写通路那一轮的同一断言是 20,960，差额是读臂现在也是请求拍；同批请求里 bit 12 置位 **16,768** 次是**读通路那一轮之前**的数字，本轮**没有**单独留存）。
- **`PPUCTRL[4]`（背景 pattern table）与 `[5]`（精灵 pattern table）在写地址里不起任何作用。** 它们是**取数**侧的"FETCH 表选择"：背景 `bg_tile_base` 的 bit 12 和精灵 `s_pat_addr` 的 bit 12 是由它们驱动的。写地址的 bit 12 来自 `v_addr[12]`，也就是 CPU 用 `$2006` 装进去的那一位。真机也是这样：程序用 `$2006` 指向哪个 CHR 字节就写哪个，与 PPUCTRL 的表选择位无关。反过来说，如果写地址错用了 `PPUCTRL` 的位，程序就会在 `PPUCTRL[4]=1` 时把本该写进 table 0 的字节写进 table 1——**在 T0 那条忽略对上会立刻显形**：CHR-ROM 板与 CHR-RAM 板在同一条程序下渲染出不同的图。
- **`chr_ram_we` 里那句 `ppu_addr[13] == 1'b0` 因此永远成立。** 它不是"保护 bit 13"，而是对"外部 CHR 一直只有 8 KiB"这一既有约定的一次重复断言；`system-v6` 的 P0-3 在 96 个写拍上重新核对 `chr_final_addr[13]` 置位 0 次，写侧的 W1 断言里也逐拍核对 `chr_waddr[13] == 0`。

## 3. 为什么 `chr_we` 必须是组合的、而且恰好 1 `clk` 宽

```verilog
assign chr_we = !reset && reg_cs && reg_we && (reg_addr == 3'd7)
                && (v_addr < 15'h2000);
```

- `reg_cs` 是**单 `clk` 脉冲**，只在 `div_phase == 0` 那一个时钟上为高（寄存器访问在 `clk` 上升沿完成，**不受 `ce` 门控**）。所以 `reg_cs` 本身已经是 1 `clk` 宽，`chr_we` 与它同宽。
- **如果把 `chr_we` 改成寄存器输出，它就会与内部路径的 `chr_ram` 写错开一个时钟。** `g_chr_internal` 那一支的写是 `always @(posedge clk)` 里用**同一个沿**完成的（`if (ce)` 内 `chr_ram[v_addr[12:0]] <= reg_din`）。外部路径要在**同一个沿**上被外部存储器看到 strobe，就必须让 `chr_we` 在那个沿之前已经是高——也就是组合地由 `reg_cs` 导出。W2 那组断言"连续两个 `ce` 上 `chr_we` 为高的拍数 = 0"就是在钉这件事：如果错开一拍，写就会变成 2 `clk` 宽，物理存储器会当成两次写。
- **`!reset` 而不是让复位覆盖。** 复位期间 `reg_cs` 已经是 0，但显式写出 `!reset` 让"复位窗口内 `chr_we = 0`"成为这条赋值自身的性质，而不是 `reg_cs` 的副作用。P0-1 就在复位窗口内断言 `chr_we = 0` 且 `chr_waddr = 0`。
- **`reg_addr == 3'd7` 而不是 `reg_addr[3:0] == 4'd7`。** `reg_addr` 就是 `cpu_addr[2:0]`，$2000-$2007 八个寄存器折叠在 3 bit 上。

## 4. 仲裁：写与读**不再共用**一根地址线（`274e25a`）

`nes_system_v6` 里 CHR 地址总线是 mapper 与两个取数单元共用的。v5 把 `mapper_ppu_addr` 绑 0；写通路落地那一轮把它改成**写优先**的组合 mux：

```verilog
wire [13:0] mapper_ppu_addr = ppu_chr_we ? ppu_chr_waddr : ppu_chr_addr;
wire        mapper_ppu_we   = ppu_chr_we;
```

**那根 mux 已经删掉了**（`274e25a`）。现在是：

```verilog
wire [13:0] mapper_ppu_addr = {ppu_chr_we ? 1'b0 : ppu_chr_addr[13],
                               ppu_chr_addr[12:0]};
wire        mapper_ppu_we   = ppu_chr_we;
```

- **为什么可以删。** CHR 阵列本来就有一条**与读地址无关的写地址**：`nes_cart_rom.v:193-197` 在 `chr_rindex` 旁边声明了 `chr_windex = chr_waddr[CHR_LOCAL_BITS-1:0]`，zynq 顶层也已经把它接上。共用一根地址的地方**在 mapper 上游**，就是上面那根 mux。删掉它同时删掉了 14 bit 的 2:1 选择器和"写要冻结取数单元"这件事的**存在理由**。
- **为什么只替换 bit 13，而不是整根字。** 这一位是 testbench 逼出来的更正。`nes_mapper.v:221` 的 `chr_ram_we` 是 `chr_ram_enable && ppu_we && !ppu_addr[13]`，而写拍上它过去看到的是 `ppu_chr_waddr[13]`——**结构上恒 0**，因为 `chr_we` 被 `v_addr < $2000` 限定。读地址在那里**不是 0**：`nes_chr_fetch_unit.v:36` 把 `fwd_addr` 算成 `nxt_addr + 8`，`bg_tile_base` 顶到 `0x1FFF`，所以 `bg_chr_addr_raw` 会到 `0x2007`。直接换成裸的 `ppu_chr_addr` 时，系统 bench 那块板**拒绝了 11 次合法的 CHR-RAM 写**。把写地址的 bit 13 放回写拍上，`chr_ram_we` 就与改动之前**逐位相同**，而每个 mapper 叶子真正消费的 **bits 12..0 完全没有 mux**。
- **写不抑制读。** `chr_req` 由取数单元**与读臂**经组合 mux 产生，**写不会把它拉低**。所以 `chr_req` 与 `chr_we` 在同一个 `ce_ppu` 上**仍然可以同时为高**——这条不是缺陷而是硬件形状：2C02 只有一根 CHR 地址总线，2C02 自己也是写优先。TB 把这件事**测量**出来而不是假定：`system-v6` 的 `P0-2 WRITE-READ-ARBITRATION` 数出 W1 板的 96 个写拍里有 **22** 拍与在飞的背景取数拍撞在一起。
- **撞上那一拍现在什么都拿不走了。** 取数单元收到的是**它自己的字节**，所以它不需要任何保护；`chr_hold_bg` / `chr_hold_sp` 里**不再有 `chr_we`**（`00ca051` 那轮曾经是 `(chr_rd_win || chr_we) && <unit>_chr_req`）。原先那一拍要改用**写模型**核对 `chr_final_addr`，现在按**读模型**核对，因此**被排除出读翻译计数的拍数消失了**，那条计数在**全部**拍上仍然精确。
- **代价写在明处。** CHR 阵列第一次在同一 `clk` 上被读和写，两个地址可以重合。见 8.3。
- **这一改动的收益是实测的，不是推断的。** 修复前那根 mux 背后的冻结，因为背景取数流水**零余量**（`bg_fetch_due` 每 **8** 个 `ce` 触发一次、一个 tile 占 **8** 个 `ce`；**一个 dot 是一个 `ce`，不是三个**），每次撞车都丢掉一整个请求：`tb/ppu/tb_bg_fetch_drop.v` 在一个刻意非均匀的 nametable 上量到写侧单独贡献每三帧 **3,142** 次丢弃与 184,304 个像素里的 **8,317** 个错像素。删掉 mux 之后写侧是 **0** 次丢弃、**0** 个错像素，**100%** 的写侧损伤消失。

## 5. `chr_ram_enable` 门与 CHR-ROM 忽略行为

`nes_mapper.v:221`：

```verilog
assign chr_ram_we = chr_ram_enable_r && ppu_we && (ppu_addr[13] == 1'b0);
```

`chr_ram_enable_r` 由 mapper 决定：NROM/UxROM 在 CHR-RAM 板上为 1、在 CHR-ROM 板上为 0。所以**同一份程序、同一批地址、同一批字节**，在 CHR-ROM 板上这一拍被门挡住、什么都不写。

`system-v6` 用**两块板配成一对**（`chr_rom` 是 `ab_v6` 的 `NROM_CHR_RAM=0` 孪生，程序字节完全相同）把这件事变成一条可证伪的断言：

| 检查 | 实测 |
| --- | --- |
| 配对前提：两块板的 strobe 数必须相等，否则配对结果无意义 | **96 vs 96** |
| `mapper_chr_ram_we` 在 CHR-ROM 板的 96 个写拍上为低的拍数 | **0**（即 96 拍全为低）；`chr_ram_enable` 在该板上是 **0** |
| 同一拍 `chr_wdata` 是否仍等于 PPU 的 `reg_din`（数据没被门吞掉） | **0** 拍不等 |
| CHR-ROM 板 128 KiB 阵列中与运行前快照逐字节不同的字节数 | **0 / 131,072** |
| CHR-ROM 板的图像是否已经是程序要写的那 48 字节（ROM 卡带语义） | 是（err = 0） |
| 两块板在最后一帧整帧的画面 | **完全相同**（`PIXELS_PER_FRAME * 4` 个 clk 采样、0 处 pixel-index 差异、0 处几何差异） |

**"配对行"必须成对读。** 单独看 CHR-ROM 板那一半，它只证明"写被挡住了"；成对看才有意义：同一 strobe、同一地址、同一数据，**两种相反的结果只由一个 elaboration 参数决定**。TB 把 CHR-RAM 那一半写成活的对照片（live control）而不是形式：同一程序同一地址下 CHR-RAM 板改了 N 个字节、CHR-ROM 板改了 0 个。

**为什么 `ab_v6` 本身必须是 `NROM_CHR_RAM = 1`。** `mapper_chr_ram_we` 为 0 时写通路在这个 testbench 里是**结构上死的**（TB 的 `chr_mem` 写入被 `chr_we && mapper_chr_ram_we` 门住），什么都不会被观测到。把 phase 1 的实例做成 RAM 板，正好让 **P0-4 整帧 A/B 自己变成这条通路最强的检查**：`ab_v5` 的内部 `chr_ram` 与 `ab_v6` 的外部 `chr_mem` **都从哨兵出发**，也都只可能因为程序自己的 `$2007` 写才变成 run A 的图像。

## 6. 非空洞：哨兵、字节级核对与自验证对

**"写通路存在"和"写真的落地"是两件事。** 一条死通路也能让"每次写都产生一个 strobe"这条断言全绿。所以本轮用三组互相独立的办法把它钉死。

### 6.1 哨兵：预载的是程序所写的**逐位取反**

每块 CHR-RAM 板的 128 KiB 图像**跨每一个 4 KiB 块**都预载成程序要写的**补值**：

| 板 | 程序上传 | 预载哨兵 |
| --- | --- | --- |
| `ab_v6`（NROM CHR-RAM） | `ff 00 00 ff ff 00` | `00 ff ff 00 00 ff` |
| `chr_ram_b`（自验证对的另一半） | `00 ff ff 00 00 ff` | `ff 00 00 ff ff 00` |

`ab_v5` 的内部 `chr_ram` 也从同一个哨兵出发。这样"漏掉一次写"的后果是**确定的、看得见的**：该处像素会显示哨兵那一档的 pattern 值（index 2）而不是程序那一档（index 1），于是 **P0-4 的逐 `ce` 整帧 A/B 与 P0-5 的具名像素类两条同时失败**。

### 6.2 字节级核对（在程序自己置起的 `ram[0015]` 标志上）

| 检查 | 实测 |
| --- | --- |
| 96 个写拍 vs **总线侧**独立统计的"进入 CHR 半区的 `$2007` 写"数 | **96 vs 96**（相等 → 每一次写恰好产生一个 strobe） |
| mapper 接受的拍数 | **96 / 96** |
| 写拍地址翻译错 | **0** |
| 连续两个 `ce` 上 `chr_we` 为高的拍数 | **0** |
| 在程序标志处，96 个字节里不等于程序自己那个常量的 | **0** |
| 在程序标志处，96 个字节里**仍然是哨兵**的 | **0** |
| `chr_mem[$2000+d]`（超出 PPU 能产生的**每一个**地址，`chr_final_addr` 顶到 `$1FFF`）的 48 个字节是否仍为哨兵 | **是，48 / 48，0 处不符** |

最后一条是"写到的地方**恰好**是程序瞄准的地方、别处一个字节都没动"的可观测形式。

### 6.3 自验证对：`chr_ram_b` 用**字节完全相同的代码**跑**互补的图像**

`chr_ram_b` 与 `ab_v6` 跑**同一份代码**，两份 PRG 镜像之间**只有程序填充循环读的那两个数据单元**不同。于是一次运行上传 run A 的图像、另一次上传 run B 的图像，两块板都从**互补的**哨兵出发。

- strobe 拍数相等（不等就直接 `$fatal`，否则下面的比较无意义）。
- `chr_ram_b` 的字节最终等于 run B 图像的**全部**命中；**错误地仍停在 run A 图像上的字节 = 0**。
- 最后一帧整帧按 4 `clk`/dot 采样：**245,760** 个 clk 采样、**0** 处几何差异（说明两次运行真的一拍不差地在锁步），而**画面在这 245,760 个采样上全部不同**，其中 **15,360** 个落在可见扫描线**最左边 16 列**——正是程序写的 BG tile 0 与 tile 1 被画出来的地方。

**为什么这条能免疫"完全死的通路"**：如果 `$2007` → CHR 两边都被忽略，两块板会各自渲染自己的哨兵，两张图会**相同**，这条断言因此**失败**。它不是"两张图不一样"的弱检查，而是"必须不同且必须不同在指定位置"的强检查。

## 7. MMC3：写是被 mapper bank 限定的，不是平铺的本地 RAM

在 `chr_mmc3`（`MAPPER_SELECT=4`、`MMC3_CHR_RAM=1`）上跑**3 个写拍**：3 个产生 strobe、3 个被接受、写拍翻译错 **0**、连续 `ce` **0**。

| 步骤 | `r0` 写值 | 寄存器值 | 本地地址 | 落点 `chr_final_addr` |
| --- | --- | --- | --- | --- |
| W2-1 | `$00` | `$00` | `$0040` | **`$00040`** |
| W2-2 | `$42` | `$42` | `$0040`（**同一个本地地址**） | **`$10840`**（与上一步相距 **67,584** 字节） |
| W2-3 | `$42` | `$42` | `$0840`（bit 11 置位） | **`$10C40`**（选中 r0 的**奇 1 KiB**） |

**非空洞**同时被钉住：两个 `r0` 值是 `$00` 与 `$42`、两个结果地址相距 67,584 字节；第一处目标正上方那个控制单元仍持有它的 `$5A` 预载值；**跨整个 128 KiB 阵列恰好 1 / 1 / 1 个字节改变，且别处一个都没有**。三个写、三个不同的翻译地址 → 存储是**被 `nes_mapper_mmc3` 做了 bank 限定**的，不是一块平铺的本地 RAM。

### 7.1 一个必须记住的坑：`$2006 = $1000` **到不了 R0**

`nes_mapper_mmc3.v:110-112`：

```verilog
assign chr_window_base = ppu_addr[12]
    ? {1'b1, ppu_addr[11:10]}
    : {2'b00, ppu_addr[11]};
```

**bit 12 置位选的是 window 4..7（即 R2..R5），R0 / R1 只有在 bit 12 为 0 时才可达。** 所以：

- 任何"经 MMC3 写 CHR"的文档示例，若要命中 R0，**必须用低于 `$1000` 的本地地址**（上表里的 `$0040` 就是），否则它落到的是 R2..R5 里的某一个，而且 R0 的值在 bit 12 置位时**根本没被参考**；
- 只想说明"地址会跟着 bank 变"的例子，则**必须写明它实际命中的是哪个窗口**，否则读者会按 R0 去理解而得到错误的期望地址；
- 这条也解释了上表 W2-3 用 `$0840`：bit 11 置位而 bit 12 保持 0，所以在 R0 内部选中了奇 1 KiB。

## 8. 必须继续说的四件事

### 8.1 `$2007` **读** CHR 已实现，但读**占掉**了总线上一个取数拍（撞车仍未修）

**这一节在读通路那一轮被整段改写。原文写的是"读仍返回 0、写通了读没通"，那句话已经不成立。**

现在的形状是：`nes_ppu2c02` 新增 `input wire chr_rd_arm`，`g_chr_external` 里 `$2007` 的 CHR **读**是 CHR 总线的**第三个 master**：

```verilog
assign chr_rd_win = chr_rd_arm && (v_addr < 15'h2000);
assign chr_req  = chr_rd_win || (sp_bus_sel ? sp_chr_req : bg_chr_req);
assign chr_addr = chr_rd_win ? v_addr[13:0]
                             : (sp_bus_sel ? sp_chr_addr_raw : bg_chr_addr_raw);
```

外加一个 set/hold 寄存器 `chr_rd_armed_q`，以及读分支里的 `read_buffer_reg <= chr_rd_armed_q ? chr_rdata : 8'h00;`。**`chr_rd_armed_q ?` 这一层是失效保护**：端口没接或读臂漏掉时，外部路径退化成原来那条**有文档的** `8'h00`，**而不是**悄悄返回一个取数字节。`g_chr_internal` 一行未改，所以 v5 及更早的板子继续走那条本来就能工作的组合通路。

**`chr_rd_arm` 的时序零余量。** 外部 CHR 存储器在**每一个 `ce_ppu` 沿**（`ce_ppu` 在 `div_phase` 0 / 4 / 8 触发）寄存 `chr_rdata`，而 CPU 在 `div_phase == 0` 锁存 `bus_din`。所以地址必须**提前整整一个 `ce`** 放到总线上，也就是在 `div_phase == 8` 那一拍。`v_addr` 只在 `$2007` 那一拍变，所以它在这个窗口里是稳的。**提前量恰好是零余量**——`v_addr → chr_addr → mapper → chr_final_addr → chr_rdata` 这条链上任何一处插一个寄存器都会打断它。

**首版的一个真实缺陷（已修，必须记下来，否则会被重新引入）**：首版读臂要求 `ppu_req`，而 **`ppu_req` 在 `div_phase == 8` 上结构上恒为 0**——`nes_cpu6502.v:215` 让 `cpu_active = ce && !bus_hold && !reset`（`ce` 就是 `div_phase == 0`），`nes_cpu6502.v:755` 在 `!cpu_active` 时强制 `bus_req = 1'b0`，而 `nes_cpu_bus.v:238` 的 `ppu_req = cpu_req && !bus_hold && (owner_r == OWNER_PPU)` 一路依赖 `bus_req`。于是读臂**从来没有抬起过**，每一次 `$2007` CHR 读都返回那条失效保护的 `8'h00`，新加的 testbench 在**第一个**读拍上就响亮地失败，而不是空洞地通过。修法是把 `ppu_req` 换成 `sel_ppu`、把 `ppu_we` 换成 `cpu_we`——在整个等待窗口里真正成立的项，因为只有 `bus_req` 被清掉，`bus_addr` 与 `bus_we` 从来没被清过。**`sel_ppu` 是承重的、不是装饰**：`ppu_addr` 本身只是 `cpu_addr[2:0]`（`nes_cpu_bus.v:189`），没有 `sel_ppu` 的话一次 `$4007` 的 APU-IO 读会被译码成 `$2007`，把 `v_addr` 送上 CHR 总线。

**诚实的合同（`00ca051` 之后）**：一个 `$2007` CHR 读返回的字节，在 mapper 翻译之后的那个地址上**永远正确**，任何扫描线状态都是，这一点没有变。它仍然要占掉一个 `ce` 的地址时间，而**取数单元不会再吃到一个为读采集的字节**了——撞上时那个处在 `S_BEAT` 的单元被冻结一整拍、下一拍重跑同一个请求（见 8.2）。**代价换了形状而不是消失**：背景取数流水余量为零，所以这一次冻结等于丢掉一次 `bg_fetch_due` 请求，在非均匀 nametable 上实测每三帧 **5,236** 次丢弃、184,304 个受门可见点里 **11,578** 个渲染不同。真实 2C02 也只有一根内部地址总线，所以"把地址放上总线要花掉一个 `ce`"是**忠实**而不是走捷径。在扫描线 240–260 或关渲染时可以证明**像素不可见**；扫描线 **261 明确不安全**（它的 dot 340 背景取数与 dot 259–290 的精灵预取喂的是第 0 行）。**渲染开着时的帧中 `$2007` CHR 读不宣称安全——现在的理由是请求被丢弃，不是字节被顶掉。**

**给 CHR 存储器合同新增的一条义务**：读 master 现在也会抬 `chr_req`，所以存储器必须在**每一个 `chr_req` 为高的 `ce`** 上捕获地址。它同时让**读写竞争第一次变得可观测**——testbench 把它建模成 read-first，这个建模选择现在对"写完一个 CHR 字节立刻读回来"的程序是**看得见的**。

**证据**（全部来自 `-Mode system-v6` 通过的那一次运行，逐条数字与固定输出见 [`docs/modules/system-v6.md`](modules/system-v6.md) §5.1.3 与 `tb/system/README.md`）：W3-1 `ARMED-ALWAYS` 396 个读拍对 396 个读臂一对一、每个读拍都看到 `chr_rd_armed_q=1`（违例 0）、每个读臂都在下一个 `ce_ppu` 被一个读拍消费掉（悬空 0、背靠背两个读臂 0）；W3-2 `ROUND-TRIP` 395 个读拍核对、**0 错**（本轮第一个 `$2007` 读没有前驱、被排除的 1 个），396 次读臂捕获核对 0 错、0 次因写竞争跳过，**期望值来自 TB 自己的 bank 模型与 PPU 自己的 `v_addr`、从不来自 `chr_rdata` 本身**；W3-3 `CROSSES-THE-MAPPER` 全部 396 个读臂拍上 `chr_addr == u_ppu.v_addr[13:0]`（错 0）、`chr_final_addr == (tb_chr_bank_model<<13)|(v_addr[13:0]&0x1fff)`（错 0），`mapper_chr_ram_we` 在 **0** 个读臂拍上为高、`chr_we` 在 **0** 个上；W3-4 `VALUE-TRACKS-CHR-CONTENT` 32 个回读字节逐个与各自实例的 CHR 内存比，窗口 `$0000` 在 ab_v6 / ab_v5 / chr_rom 上读回 `ff`、在 chr_ram_b 上读回 `00`，所以两块跑**字节完全相同**代码、数据互补的板子在 **32** 个单元里的 **24** 个上给出不同的字节；W3-5 `UNWRITTEN-ADDRESS` 8 个未写地址在 ab_v6 上全读回 `$00`，在另外三块 run-A 板上逐个可证与刚写进 `$1020` 的字节**不同**（各 8/8）；W3-6 `SENTINEL-SURVIVES` 四个读窗口在程序标志处快照、结束时重读，**32** 个字节**一个都没动**，`chr_mem[$2000+d]` 的 48 个字节仍持哨兵，ROM 板的 128 KiB 与运行前快照逐字节相同；W3-7 `MODEL-CREDIBILITY` 复用 P0-6 的按 `ce` 影子模型，146,797 个请求拍（错 0）与 117,164 次取数单元锁存（错 0），23 / 18 次因写竞争跳过；W3-8 `CROSS-DUT-VALUE-AB` 32 个持有回读字节的 RAM 单元在 ab_v5（内部 `chr_ram`）与 ab_v6（顶层 128 KiB 阵列）之间**逐字节相同**（不同的单元 0）；W3-9 `COLLISION-IS-REAL` 396 个读臂里 **107** 个与在飞的取数请求撞在同一个 `ce` 上（**71** 个撞背景、**36** 个撞精灵），按落点分布是 **378** 个在 vblank 扫描线 240–260、**18** 个在外部（loop A、`PPUMASK=$00`），跨扫描线 93..255；W3-9b 171 组连续 `chr_req` 对里 89 组第二拍由读臂赢（80 撞背景、9 撞精灵）、82 组在读臂之后由取数赢（82 撞背景、0 撞精灵）、**0** 组两拍都没有读臂；W3-10 `INVISIBILITY-PROVEN` 396 个读臂在**臂拍本身**逐个对着写明的不可见集合核对，违例 **0**，且任何违例当场 `$fatal` 而不是事后计数。

**三条诚实的限制必须一起转述**：(1) chr_rom 的回读与 ab_v6 **不是逐字节不同**——它不可能是，因为 chr_rom 的 CHR 预载的就是程序要上传的那张图；被测的是**来源**：`chr_mem[$0000]` 运行前是哨兵 `$00`、现在是 `$FF`，而 ROM 板的 `$0000` 运行前后都是 `$FF`，并且那是一块 96 个写全部被 mapper 拒绝、128 KiB 改动 **0** 个字节的板子；(2) chr_ram_b 在 W3-5 上是**退化的**（0/8），因为 run B 的 ON 常量与 TB 装载值都是 `$00`——那块板改由窗口 `$0000` 分开；(3) `chr_mmc3` **根本不发** `$2007` 读。

**`P0-8` 是被重新界定，不是被削弱。** 它原先断言 `chr_req` 从不在两个 `ce` 上连续为高。这**不能**靠在 `mask_reg[3]` 上加条件来推广——mask 门的是像素不是总线，实测 `PPUMASK=$00` 仍产生 **3,069** 组连续对、把读限制在扫描线 240–260 仍产生 **369** 组。现在它把每一组连续对归属到**第二拍是哪一个 master 赢了**，用的是 PPU 自己选 `chr_addr` 的那条表达式，并断言**两拍都没有读臂**的连续对是 **0**——那恰好就是旧不变式覆盖的"取数对取数"性质。它另外还断言没有两个读臂相邻。`m_req_consec == 0` 逐字保留，因为 chr_mmc3 的程序不发任何 `$2007` 读。

**仍然不能宣称**：**渲染开着时帧中 `$2007` CHR 读是安全的**（撞上时取数请求被丢弃，实测每三帧 5,236 次、11,578 个可见像素不同，条件见 8.2）；片上有任何 CHR 存储；有任何上板证据；**新增义务**：多出来的这一级仲裁落在 `chr_addr` 上，而 `chr_addr` 是通往 CHR 地址的**唯一**通路，所以真实存储方案落地时，地址建立时间必须按 BRAM/SDRAM 的 `tACC` 预算重新核对。**同址同拍写读的行为现在有了一个综合读回（READ_FIRST）而不是只有建模选择，但没有任何测量碰到它**，而且它仍然不是硬件行为。

### 8.2 写的撞车已在上游关闭（L-17），读的撞车**仍然要付代价**（L-20，仍未修）

`chr_req` 不被写压制（它是取数单元 + 读臂的组合 mux），`bg_fetch_due` 也**没有**扫描线门控也没有 mask 门控，所以两者可以独立地在同一个 `ce` 上为高。实测 **96 个写拍里 22 个**与在飞的背景取数相撞。

**写那一半（L-17）不再是隐患。** 它曾经是：写优先 mux 把写地址交给取数单元，`tb/ppu/tb_chr_wr_collision.v`（回归目标 `chr-wr-arb-tb`）在**渲染开着**的可见场里推 `$2007` CHR 写，在未修复的 RTL 上量到 **5,587** 个背景与 **1,389** 个精灵取数单元吃了一个为写采集的字节，184,304 个渲染像素里 **23,006** 个与一个独立参照 PPU 不同。`263f8c1` 先用冻结挡住，`274e25a` 再把**原因本身删掉**：写不再夺读取数单元的地址，所以既不需要冻结，也没有那一拍的错字节。

**读那一半（L-20）仍然要付代价，而且代价已经改过了形状。** `chr_rd_win` 直接喂 `chr_req` 与 `chr_addr`，所以撞上时读臂**必须**拿走地址（它零余量，见 8.1）。`00ca051` 的修法不是延后读臂，而是**延后那一个拍**：撞上时把处在 `S_BEAT` 的取数单元**冻结一整拍**，它的状态与地址寄存器都不动，下一个 `ce` 重跑同一个拍。错字节因此不再被消费（未修复 RTL 上是 **4,694** 个背景 + **1,186** 个精灵单元吃错字节、184,320 个像素里 **14,943** 个不同；修完三项全 0）。

**但"延后一拍"在这条流水线上等于"丢掉请求"，因为余量是零。** `tb/ppu/tb_bg_fetch_drop.v`（**故意不进 `tools/sim_all.ps1`**，因为它测的是一个活缺陷）在刻意非均匀的 nametable 上量到：

| 模式 | 每三帧 `bg_fetch_due` | accepted | **dropped** | 184,304 个受门可见点里渲染不同的 |
| --- | --- | --- | --- | --- |
| 只读 `$2007` | 25,152 | 19,916 | **5,236** | **11,578**（6.28%） |
| 只写 `$2007`（`274e25a` 之前） | 25,152 | 22,010 | **3,142** | **8,317** |
| 只写 `$2007`（`274e25a` 之后） | 25,152 | **25,152** | **0** | **0** |
| 读写同时（之前 → 之后） | 25,152 | 22,448 → 22,534 | 2,704 → 2,618 | 5,996 → 5,774 |

损伤是**瞬态且有界**的，这一点是量出来的不是论证出来的：**开局与收尾配对相等**（**8,290 / 8,290**，结束时仍开着的为 0），4,976 段是 1 个错点、2,403 段是 2 到 9 个错点，**没有任何一段超过 9 个点**，平均每次可见丢弃 **2.4** 个错像素，范围限定在一个 8×8 cell 内。原因是结构性的：`nes_chr_fetch_unit` **不是**从流上取字节的，每次被接受的请求各自锁存 `tile_base`，而 `tile_base` 是当前 dot 的纯组合函数，`bg_fetch_due` 又按绝对 dot 节拍触发——所以一次丢弃是 tile 序列里的一个**洞**，不是移位。

**受影响条件三条同时成立**（全部从源码推出）：程序在 `v_addr < $2000` 时发 `$2007` 访问、这些访问发生在 PPU **正在取数**的时候、以及 nametable **不是均匀的**。nametable 与 palette 访问既不抬读臂也不抬写 strobe，这是一个很大的结构性过滤器；只做一次开机 CHR 上传、且上传时关渲染的程序**不受影响**。按实测的"每 5.7 次 CHR `$2007` 访问丢一次"折算，一个每显示帧做 100 次这种访问的游戏大约会看到每帧 **18** 次丢弃与 **43** 个错背景像素，散落在单个 cell 上而不是整屏移位。

- **结构性修法是给 CHR 加第二个读端口**，代价大约是 **2 个额外的 RAMB36E1 tile**。读臂**不能**被排到后面去：`D+8` 的追赶取数会在 `D+16` 才锁存、`D+17` 才开始显示，那会把瞬态散点损伤变成**永久的 8 像素水平移位**。
- **冻结逻辑在 PPU 内部、`mapper_chr_ram_enable` 的上游**（`nes_ppu2c02.v` 的 `g_chr_external` 里），而且两个冻结项都**没有** CHR-RAM / CHR-ROM 限定。所以**一块 CHR-ROM 卡带冻结取数流水线的程度与 CHR-RAM 卡带完全一样**，只有那次写会在下游被 mapper 拒绝。早先"这只影响 CHR-RAM 标题"的说法**是错的**。

### 8.3 存储与综合：推断形态已知，截止期与硬件行为仍没有落到硅上

- **片上没有任何 CHR 存储。** 那 128 KiB CHR **只活在 testbench 里**（`ab_v6` / `chr_rom` / `chr_ram_b` / `chr_mmc3` 各自一份 TB 侧模型）。真实系统需要 SDRAM，而 **SDRAM 控制器在仓库里还不存在**（TF 只有命令帧发送器）。
- **BRAM 推断现在有数字了，而且是从布线后的设计读回来的，不是从仿真推的**（`274e25a`）：CHR 阵列的 `WRITE_MODE_A` 是 **READ_FIRST**，`READ_WIDTH_A` 与 `WRITE_WIDTH_A` 都是 **4**，两处一致。对照之下 PRG ROM 推断成 **WRITE_FIRST**、`frame_mem` 是 **NO_CHANGE**，两者都不在读通路上。这回答了"推断成什么"。
- **同址同拍的写读顺序因此不再只是一个建模选择，但它仍然没有任何测量。** `274e25a` 删掉写侧冻结之后，CHR 阵列第一次在同一 `clk` 上被读和写，两个地址可以重合。推断出的 READ_FIRST 意味着同址写读返回**写前**的字节，这正是仓库里每一个 bench 的模型，也是唯一自洽的选择——取数单元没法被告知"这个字节还没生效"。**但两个碰撞 bench 报告的同址碰撞都是 0 次**，所以这条路径在仿真里**一条测量都没有**。界是**一个 tile 的一个 dot** 上一个错字节，而且只在 `$2007` CHR 写正好瞄准取数单元正在要的那一字节、并且正好在写的那一个 `ce` 时才达到。对照的代价是冻结平均每次丢弃 **2.4** 个错像素（读 11,578/5,236、写 8,317/3,142），**用 1 个点换 2.4 个点**。
- **TB 的 CHR 模型是零时序代价的。** `chr_rdata` 是"下一个 `ce` 给出"的寄存读，每 2 个 `ce` 一个字节。这个合同被断言出来了（不是假定的），但它**不证明任何真实存储器能满足 1 `ce` 寄存读的截止期**，而 `chr_req` **不是**背压。
- **没有任何上板证据。** 综合、布局布线、STA 数字都存在（RAMB36E1 **50** / RAMB18 **0** / LUT-as-memory **2**，44 / 44 引脚全部落位，DRC 与布线 0 错误，核心 setup WNS **+4.711 ns**），但**没有任何东西被烧到板子上**，所以这些数字全部是纸面结论。
- **没有任何 `set_input_delay` / `set_output_delay`**，因此 **6 个输入与 34 个输出端口是未约束的**。
- **读通路新增的义务（`$2007` 读那一轮登记，仍然有效）**：(a) 存储器必须在**每一个 `chr_req` 为高的 `ce`** 上捕获地址，因为读 master 现在也会抬 `chr_req`；(b) 多出来的那一级仲裁落在 **`chr_addr` 上**，而 `chr_addr` 是通往 CHR 地址的**唯一**通路，所以 `v_addr → chr_addr → mapper → chr_final_addr → chr_rdata` 的建立时间必须按真实存储器（BRAM / SDRAM）的 `tACC` 预算**重新核对**；(c) 删掉 mux 之后地址链上少了一级 14 bit 选择器，这是**改善**，但建立时间的预算仍然没有被核对过。

## 9. 与既有缺陷并列的记录

以下两条**先于本轮就存在，本轮刻意没动**（修任何一条都会对称地改到 `g_chr_internal` 并波及 10 个以上回归目标）：

- **`write_toggle`（`w`）不会被 `$2007` 写清除。** 真机上一次 `$2007` 写会把 `w` 清 0，所以紧接着的 `$2006` 被当成"第一次"；这里不会。软件如果依赖"写 `$2007` 顺手重置 `w`"，行为会不同。
- **`read_buffer_reg` 在写时不清。** 真机上写 `$2007` 会把读缓冲填成"被写掉的那个字节对应的镜像地址"；这里保留旧值。

`ppu-external-chr.md` 第 8 节登记的三条行为差异里，**8.1（写 CHR 后渲染晚 1 dot）现在才第一次有了一条真实通路可以被测量**；写通路那一轮没有为此单独构造场景，**读通路那一轮也没有**，所以**它仍然既没有被量化、也没有被验证**。8.3（`$2007` 读 nametable 区间别名到 CHR 前 8 KiB）**既没有被实现也没有被验证**——读 arm 只在 `v_addr < $2000` 时才抬，而 nametable / palette 的读仍然走 PPU 自己的 `ppu_space_read`，所以别名行为原样保留。

## 10. 证据边界（必须一起转述）

- **可以说**：`$2007` 写 `< $2000` 会产生**恰好 1 `clk` 宽**的 `chr_we`，地址是自增前的 `v_addr`、数据是 `reg_din`；96 个写拍、0 翻译错、每拍一个 strobe；哨兵非空洞、字节级核对 96/96、自验证对在 245,760 个采样上全部不同、CHR-ROM 忽略对 0/131,072 改变、MMC3 三写落三个不同地址。回归目标 `system-v6`。**本文件描述的读通路那一轮**最近一次全量门是 `Result: PASS (51 of 51)`；此后 CHR 侧又过了四轮缺陷修正（`00ca051` 读臂、`263f8c1` 写碰撞、`d128a8c` 测量、`274e25a` 删 mux），**当前 HEAD `274e25a` 的全量门是 `Result: PASS (62 of 62)`、目标数 62**，上面的数字属于它各自那一轮的运行，**不要跨轮相加**。
- **可以说**：`$2007` 读 `< $2000` 的**字节值**在 mapper 翻译后的地址上永远正确，并且它**经过 mapper**（不是私有旁路）、**不抬起** `mapper_chr_ram_we`、**不与** `chr_we` 的捕获沿重合。逐条数字见 §8.1。
- **不可以说**：**渲染开着时帧中 `$2007` CHR 读是安全的**（撞上时一次背景取数请求被丢弃，扫描线 261 明确不安全）；**写与读的撞车都未修**（写侧已在上游关闭：mux 删除、写不再夺读取数单元的地址、写侧丢弃与错像素都归零；**读侧仍是开放的**，L-20）；片上有任何 CHR 存储；有 M9K 以外的真实存储器截止期证据；**地址建立时间仍然够**（真实存储器的 `tACC` 预算没有被核对过）；**同址同拍写读的行为是已证明的**（推断读回是 READ_FIRST，与 bench 的模型一致，但两个碰撞 bench 的同址碰撞都是 0 次，这条路径没有任何测量）；有任何 fmax / 面积 / STA / 上板结论——纸面的综合数字存在，**硬件证据一条也没有**。
- **整体边界**：全部证据来自 **Icarus Verilog 下的 RTL/TB 内部一致性**，是**测试台驱动场景**的 A/B 与字节核对，**不是实机卡带、不是 NESdev test ROM、不是硬件**。`system-v6` 那条整帧 A/B 本身是**背景对比**；精灵像素等价性仍然只由 `ppu-ext-chr-tb` 一条提供。**没有跑过任何真实卡带或 `nes-test-roms` 二进制**——harness 还没有真实 ROM 装载。
- **本轮 `ppu-ext-chr-tb` 的 A/B 数字逐字节未变**（**写通路那一轮与读通路那一轮都是**）：`S3` 七个精灵可观测量全部 `= 0`，`A3 verified request addresses=337450 verified latched plane pairs=126546`，`S2 request_beats=159296 … shadow_byte_mismatches=0`。也就是说**读写两条通路的加入都没有让 PPU 的渲染行为发生任何漂移**。
