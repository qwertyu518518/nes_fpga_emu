# 04 片上存储、同步 RAM、FIFO 与跨时钟缓冲

## 1. 器件存储资源的正确理解

### 1.1 已确认事实

- **【已确认事实】** 例程 Fitter 报告给出 423,936 memory bits，约 52,992 byte，即约 51.75 KiB。
- **【推断（2026-09-30 登记）】52,992 byte 是"bit 数除以 8"的换算值，不是可实现的字节容量。** 一个 M9K 是 9,216 bit；在 8 bit 负载下它只能配置成 9 bit 模式，即 **1,024×9 = 9,216 bit，每块提供 1,024 byte**。因此 46 块的实际可用负载是 **47,104 byte（46.0 KiB）**，比 52,992 byte 少 5,888 byte。**`9,216 / 8 = 1,152` 不是器件支持的 M9K 模式**：第 1.2 节列出的位宽是 1 / 2 / 4 / 9 / 18 / 36 bit，8 bit 不在其中。**做容量判断时用 47,104 byte，不要用 52,992。** 逐数组的 M9K 估算表与更正后的数字见 [`docs/00-overview/risk-register.md`](../00-overview/risk-register.md) 的 R-04。
- **【实测】片上 PPU 到现在一次都没有用掉 BRAM。** 2026-09-30 的 PPU 单独综合（`D:\quartusProject\ppu_synth2\final_ext.fit.rpt` 与 `final_int.fit.rpt`）报 `Total memory bits ; 0 / 423,936 ( 0 % )`、`Embedded Multiplier 9-bit elements ; 0 / 46 ( 0 % )`，网表里没有任何 `altsyncram` / MLAB。**因此"BRAM 够不够"目前不是本项目的绑定约束**（逻辑单元才是），但这**不代表**现有数组可以被重构成 BRAM——那种改法一次都没被测过。完整登记见风险登记册第 10 节。
- **【已确认事实】** `8_ip_ram` 生成的 RAM IP 是 Cyclone IV E 单端口、32×8 bit、输出寄存器旁路的 `altsyncram` 配置。
- **【已确认事实】** `9_ip_fifo` 的生成 FIFO 为 8 bit、256 深度，读写时钟在例程顶层相同；生成文件标记为双时钟 `dcfifo`，同步延迟参数为 4。
- **【厂商例程观察】** SDRAM 工程的两个 FIFO 是 16 bit、1024 深度，分别作为用户写侧到 SDRAM 控制域、SDRAM 控制域到用户读侧的缓冲。

### 1.2 预算不要只看“总 bit 数”

BRAM 的有效组织方式会影响可用容量、端口和读写冲突。例如同样是 16 bit 宽：

- 16 bit×N 可能使用若干 M9K 块并限制深度；
- 8 bit×2N 可能更容易适配某些端口，但不一定更省；
- 1/2/4/9/18/36 bit 等宽度配置可能有不同打包效率；
- 单口、双口、读写同址和字节使能会带来额外资源或行为差异。

因此 NES 工程的容量表应至少列出：逻辑深度、数据位宽、端口模式、预估 M9K/BRAM 数量、旁路/输出寄存器、FIFO 同步延迟和复位策略。

## 2. 同步 RAM 的读延迟

### 2.1 基本模型

同步 RAM 的典型行为是：在某个时钟沿采样地址和读使能，经过内部存储器访问后，在之后的一个或多个时钟沿给出数据。它与“组合读 RAM”不同；不能假设地址改变后 `q` 同一周期立即有效。

本项目的学习重点不是背一个固定延迟，而是为每个 RAM 接口建立表格：

| 项目 | 必须回答 |
|---|---|
| 地址何时有效 | 在地址寄存器更新后还是同一拍 |
| 读使能何时有效 | 是否可以连续拉高 |
| 数据何时有效 | 读请求后第几个上升沿 |
| 输出是否再寄存 | RAM 内部输出寄存器是否旁路 |
| 读改写 | 同址读写返回旧数据、新数据还是未知 |
| 复位 | 输出是否清零、是否初始为 X |

### 2.2 延迟对齐

如果地址、长度、字节计数和读数据一起流动，所有控制信息必须经过相同的流水级数。一个常见的概念流水级是：

```text
请求级：地址、读使能、请求号
地址已发出：IP 正在访问
数据返回：数据和对应的请求号
消费级：只在该级使用数据
```

请求号或 tag 是防止连续读取时把返回数据误认为当前地址数据的手段。对 PPU 来说，滚动、精灵和 nametable 读取可能跨越多个流水线级，不能只延迟 RGB 数据而漏掉坐标和命中标志。

### 2.3 厂商 RAM 例程的观察边界

**【厂商例程观察】** `8_ip_ram` 的控制器循环改变地址并产生读使能，但主要目的是让 SignalTap 观察 RAM 读写，并没有展示高吞吐连续读、背压或多个未完成请求。它不能作为 NES PPU 读延迟的完整参考。

**【风险提示】** 如果在 RTL 中用组合地址加法器直接读 BRAM，工具可能无法按预期推断存储器，结果会消耗 LE、增加延迟并破坏时序。学习阶段应先使用明确的 IP/存储器原语和波形验证。

## 3. 单口、双口和 FIFO 的选择

| 场景 | 推荐结构 | 关键点 |
|---|---|---|
| 同一时钟读写一个小表 | 单口 RAM | 读写不能在同一周期无仲裁地冲突 |
| 写侧和读侧同一时钟 | 单时钟 FIFO | 只需处理满/空和读写请求 |
| 写侧、读侧不同时钟 | 双时钟/异步 FIFO | 指针跨域必须安全，满空要保守 |
| PPU 同时更新和读取帧缓存 | 真双口 RAM 或 ping-pong BRAM | 明确端口所有权和撕裂风险 |
| SDRAM 控制器与用户时钟不同 | 异步 FIFO | 吸收突发、平均速率差和突发延迟 |
| NES CPU 与 PPU 共享 RAM | 按 NES 访问时序仲裁 | 总线冲突和 PPU 奇偶相位优先 |

### 3.1 双口 RAM 的端口所有权

双口 RAM 的 A/B 端口不天然等于“读时钟/写时钟”。需要定义：

- 哪个端口负责写入；
- 哪个端口负责读取；
- 是否允许同一地址同时读写；
- 每个端口的地址使能和字节使能如何定义；
- 端口复位是否影响另一端口。

## 4. FIFO 的四个视角

阅读任何 FIFO IP 都先画四个信号组：

1. 写侧：写时钟、写请求、写数据、写满、写空（若提供）。
2. 读侧：读时钟、读请求、读数据、读空、读满（若提供）。
3. 存储状态：当前指针、已使用字数、almost-full/almost-empty。
4. 复位和异常：清空、溢出、下溢、错误标志。

“满”和“空”必须在各自时钟域中同步到对侧，不能把写侧 `full` 直接接到读侧使用。

## 5. 同步 FIFO 与异步 FIFO

### 5.1 同步 FIFO

写和读使用同一个或已知同步的时钟。指针同步较简单，但仍需处理：

- 写请求和读请求的同周期优先级；
- 满时空的边界；
- 写使能和读请求是否允许连续拉高；
- 复位时数据和指针的清空；
- `show-ahead` 与普通读请求的差别。

**【厂商例程观察】** `9_ip_fifo` 顶层把 `wrclk` 和 `rdclk` 都接 `sys_clk`，属于同频同步使用示例；IP 文件本身是双时钟 dcfifo。写端和读端通过 `wrfull/wrempty` 与 `rdfull/rdempty` 观察接口，虽然没有演示真正异步时钟。

### 5.2 异步 FIFO

写指针在写域递增，读指针在读域递增。跨域传递指针时，常用二进制指针转格雷码，再经过两级同步器：

```text
写域：二进制写指针 → 格雷码写指针 → 读域同步器 → 读域比较
读域：二进制读指针 → 格雷码读指针 → 写域同步器 → 写域比较
```

关键设计点：

- 格雷码转换必须在二进制指针变化前完成，保证跨域每次最多一位变化；
- 同步器级数要足够，并按 Cyclone IV 资源和时序报告检查；
- 满判断通常比较“写指针与读指针的当前值和格雷化后的回绕值”；
- 空判断比较读写指针相等；
- 输出满/空要保守，避免数据丢失或重复；
- 指针位宽增加一位用于区分“空”和“满”；
- 复位必须同时清空两侧状态，不能只清一个域。

**【厂商例程观察】** SDRAM 例程生成的 FIFO 标记 `CLOCKS_ARE_SYNCHRONIZED` 为 1（即 IP 认为时钟同步/相关），而 `9_ip_fifo` 标记为 0。若本项目把 50 MHz、25 MHz、100 MHz、BCLK 等真正异步时钟直接套用，参数和工具检查必须重新确认。

## 6. 背压和水位

### 6.1 写侧不能一直写

FIFO 满时，上游必须停止产生新数据，或进入可重试状态。对于 TF 到音频：

- TF 读出平均速率可能高于或低于音频消费速率；
- 读到扇区边界时会出现突发空闲；
- 音频 FIFO 需要保留多个音频帧，避免 SD 卡瞬时延迟造成爆音；
- 水位过低时应暂停/重试读取，不能假定每一拍都有数据。

对于 PPU 帧缓存：

- PPU 请求像素的速率由 NES 域决定；
- VGA 读出速率固定为 25 MHz；
- 若一帧缓存不能跨域安全切换，至少需要双缓冲或行缓存。

### 6.2 读侧不能无条件读

读请求必须受空标志和协议边界控制。`rdempty` 在某个域可能比实际同步状态更早或更晚变有效；稳健设计应使用 IP 规定的保守标志，而不是把单周期空当作“下一拍必有数据”。

### 6.3 音频 FIFO 的额外语义

音频 FIFO 的元素不是“任意字节”，而是一个固定格式的音频 beat：

- 16 bit 还是 32 bit PCM；
- 左右声道如何打包；
- 是否需要字节交换；
- 32 bit 容器的高 16 bit 是否为 0、符号扩展或另一个声道；
- BCLK/LRC 每个声道采样多少 bit。

这些格式问题在 FIFO 满空之外，还必须在接口层固定。

## 7. 资源和吞吐预算

### 7.1 简单估算

给定数据宽度 `W`、深度 `D` 和时钟频率 `F`，理论有效带宽为：

```text
带宽 = W × 每拍传输元素数 × F
```

例如 16 bit、25 MHz、每拍一个元素的理论带宽约为 50 MB/s（十进制）。VGA 640×480 RGB565 若每个像素每帧都从外部存储读取，原始需求是：

```text
640 × 480 × 2 byte × 59.52 ≈ 36.6 MB/s
```

如果只从片上 BRAM 读取，25 MHz 理论上可以提供约 50 MB/s，能满足一帧流式读取但余量不大；若同时有 NES 读、音频和 SDRAM 仲裁，就更需要行缓存/双缓冲。

### 7.2 不能用理论峰值掩盖协议开销

- SDRAM 读有 CAS、刷新、预充电和总线 turnaround；
- TF SPI 有命令、响应 token、等待和数据 CRC；
- VGA 有消隐期，不能在所有周期都假定有有效像素；
- FIFO 同步和仲裁会减少可用周期；
- 读延迟和流水线 tag 会占用额外寄存器。

预算表应至少给出“峰值”“保守平均”“最坏突发”和“平均 FIFO 水位”四列。

## 8. 针对 NES 项目的存储层次

建议把存储分成四层：

1. **寄存器/小表**：状态机、颜色表、少量查表数据。
2. **片上 RAM**：PPU nametable、palette、OAM 缓存、帧行缓存。
3. **片上 FIFO**：CPU/PPU、VGA、TF、音频之间的边界。
4. **SDRAM**：完整 NES ROM、PRG/CHR、较大的 nametable/帧缓存或音频资源。

在 BRAM 紧张时，先评估：

- 是否真的需要整帧 RGB565 缓存；
- 是否可以只缓存行或 tile；
- ROM/CHR 是否只读，能否使用更适合的单口/双口组织；
- FIFO 深度是否能吸收最长外部突发延迟；
- 是否把 CDC 逻辑误当成了普通寄存器。

## 9. 验证方法

### 9.1 仿真

- RAM 连续地址、随机地址、边界地址、同址读写分别激励。
- FIFO 覆盖空→写、写→满、满时继续写、读→空、空时继续读、同时读写和复位。
- 异步 FIFO 用不同时钟、非整除频率、随机暂停读时钟测试。
- 每次读请求附带 tag，验证返回数据和地址对应。

### 9.2 板级

- 用已知递增/递减图案穿过 RAM、FIFO 和 SDRAM。
- 在 SignalTap 或外部逻辑中同时观察地址、写使能、读使能、数据、满空和水位。
- 观察 FIFO 水位是否长期贴近满/空；长期贴满是吞吐不足，长期贴空是供给不足。
- 读写同址和边界模式要重复运行，避免只在顺序访问下“看起来正确”。

## 10. 本章结论

- 同步 RAM 的核心是延迟、对齐和同址读写语义；例程的简化循环不能替代完整接口设计。
- FIFO 不是“数组加读写指针”，而是两个时钟域之间的协议和背压。
- NES 的 CPU/PPU、VGA、TF、音频和 SDRAM 必须用明确的 RAM/FIFO/双缓冲边界连接。
- 真正分配资源前，要按位宽、深度、端口、同步延迟和吞吐率做预算。
