# NES 软件学习文档总索引

## 0. 这套文档要解决什么问题

本目录面向已经熟悉嵌入式 C、只学过基础 Verilog 的学习者。目标不是把某个 C 模拟器逐行翻译成 RTL，而是建立一条可以反复验证的认知链：

```text
游戏 ROM 的字节
      ↓
CPU 看到的地址、总线周期、寄存器变化
      ↓
PPU/APU/DMA 与 CPU 的时间关系
      ↓
C 参考实现中的模块和状态
      ↓
可综合的状态机、存储器和总线
      ↓
能够解释失败原因的波形与断言
```

学完本目录后，应能回答以下问题：

- 一个 CPU 地址为什么会被送到 RAM、PPU、APU、控制器或卡带？
- 6502 的一个指令周期中，哪些访问是真正读写，哪些是 dummy access？
- PPU 的 `v`、`t`、`x`、`w` 如何组成滚动地址？一次后台图块取数要经过哪些 PPU dot？
- OAM DMA、DMC DMA、mapper IRQ 如何改变 CPU 的时间线？
- iNES 文件头的每一个相关位如何影响 PRG、CHR、mirroring 和 mapper？
- 参考 C 代码中哪些是实现选择，哪些是 NES 硬件行为，哪些明显是简化或 TODO？
- 当把 C 状态机搬到 RTL 时，状态、数组、回调、动态内存和等待周期分别应如何落地？

阅读源码时采用下面的证据等级。等级越高，越不应该被 C 代码的具体写法替代。

| 标记 | 含义 | 可以得出的结论 |
|---|---|---|
| `[源码观察]` | 在上述提交中实际读到的文件、函数、字段或行为 | 这个版本如何组织软件、哪些路径被执行、作者留下了什么 TODO |
| `[NESdev 真值]` | NES 硬件/官方行为模型和测试 ROM 所约束的行为 | 目标是模拟真实硬件时应满足的外部可观察行为 |
| `[RTL 建议]` | 将行为转成可综合结构的工程方案 | 不是历史硬件声称，而是本项目的实现取舍 |

`[源码观察]` 不等于 `[NESdev 真值]`。参考实现可能遗漏功能、采用近似、把复杂状态压缩成一个函数，或者在注释中承认“unsure”。文档会明确标出这些差异。涉及硬件行为时，优先级是：

```text
NESdev 行为说明与可重复测试
        >
实测波形、测试 ROM 和标准件行为
        >
多个独立模拟器中相互印证的行为
        >
某一个 C 参考实现的内部状态
        >
为了教学而做的简化
```

## 2. 推荐阅读顺序

### 2.1 第一次通读

1. `01-nes-system.md`：先建立整机和时间尺度。
2. `03-ines-format.md`：知道 ROM 文件如何变成 CPU 可见的字节。
3. `04-cpu-bus.md`：建立地址译码和总线周期模型。
4. `05-6502.md`：理解 CPU 怎样消耗这些总线周期。
5. `06-ppu.md`：理解视频侧怎样独立运行。
6. `07-apu.md`：理解音频侧和 DMC 的 CPU 占用。
7. `02-cnes-architecture.md`：把前述部件放回 cNES 的具体调用图。
8. `08-mappers.md`：理解卡带如何改变地址译码。
9. `09-c-to-rtl.md`：把 C 状态和数据结构映射成 RTL。
10. `10-verification.md`：建立可执行的证据链。

### 2.2 只想做最小可运行系统

如果目标是先让一个 NROM 测试程序在 FPGA 上运行，可以暂时按以下顺序：

```text
ROM 解析 → CPU RAM/ROM 总线 → reset/vector → 6502 基础指令
       → PPU 寄存器空壳 → NROM 固定映射 → 指令级 trace
```

在这条路径中，`01`、`03`、`04`、`05`、`09`、`10` 是必读；PPU 像素输出、APU、复杂 mapper 可以后补。

### 2.3 只想理解参考代码

按下面的调用方向读，不要从文件名字面猜架构：

```text
cNES/main.c
  → cNES/loader.c
  → cNES/system.c
      → c6502/cpu.c
      → cNES/ppu.c
      → cNES/mappers/*.c
      → cNES/renderer.c
```

Obara 的入口则是：

```text
Obara/main.c
  → emulator.c/init_emulator
  → mapper.c/load_file
  → mmu.c/init_mem
  → cpu6502.c/init_cpu
  → ppu.c/init_ppu
  → apu.c/init_APU
```

## 4. 统一记号

- `$` 前缀表示十六进制，例如 `$4014`。
- `PRG` 是卡带中的程序 ROM；`CHR` 是图形模式表 ROM；两者都以字节为单位。
- `dot` 是一个 PPU 时钟脉冲；`scanline` 是一行 341 个 dot 的编号。
- `CPU cycle`、`PPU dot`、`APU cycle` 不是同一个单位。比较它们时必须先说明时钟域。
- `v` 是 PPU 当前 VRAM 地址，`t` 是临时 VRAM 地址，`x` 是 fine X，`w` 是两次写入寄存器的高低字节选择位。
- `open bus` 指没有设备驱动数据线时，读值由浮空、上次总线值、地址线或具体硬件耦合决定；不能简单等同于零。
- `dummy access` 是为了满足 6502 或 DMA 时序而发生、但其数据通常不作为指令结果的访问。
- `R/W` 表示读或写方向；`A12` 是某些 mapper 监视的 PPU 地址线。
- `C6502`、`c6502` 等名称保留参考源码中的拼写；本目录不把它们误写成某个商业 CPU 型号。

## 6. 每个主题的固定学习模板

阅读任何一章的每个主题时，建议写下四个小问：

1. **源码观察**：参考 C 在哪个文件、哪个函数、哪个字段中做了这件事？
2. **NESdev 真值**：真实硬件对外部总线、寄存器、时序和边沿承诺什么？
3. **可观察差异**：如果 C 少做一次访问、晚一个 dot 或用固定零模拟 open bus，波形会怎样不同？
4. **RTL 取舍**：先实现行为还是先实现精确时序？需要哪些接口、断言和 trace 端口？

例如分析 OAM DMA 时，不应只写“`$4014` 会复制 256 字节”，而应继续问：

```text
写入 $4014 的 CPU 写周期是否立即启动 DMA？
DMA 的 dummy read 在哪个地址？
对齐条件依赖 CPU 还是 APU 周期奇偶？
256 次读和 256 次写是否都占用 CPU 周期？
OAM 地址非零时写入如何回绕？
```

## 7. 建议的实验循环

每个实验都尽量产生一个可以复查的证据，而不是只记录“画面像了”。

1. **静态阅读**：在固定提交中打开列出的文件和函数，画出调用关系。
2. **写预测**：先预测地址、寄存器、周期数和 dot，不看运行结果。
3. **采集 trace**：至少记录 `cycle`、`pc`、`addr`、`rw`、`data`、`ppu_dot`、`nmi`。
4. **构造最小输入**：用 16 字节或几百字节的 synthetic ROM，避免一开始加载完整游戏。
5. **分层比较**：先比较最终寄存器，再比较每个总线访问，最后比较 PPU/APU 边沿。
6. **记录例外**：把“源码近似”“硬件真值”“本项目暂不实现”分别列入清单。
7. **映射 RTL**：为每个 C 状态列出寄存器、下一状态、输出和异常条件。

## 8. 术语速查

| 术语 | 简短解释 |
|---|---|
| CPU | 执行游戏 PRG 的 6502 核心 |
| PPU | 生成视频信号、维护 nametable/OAM/palette 的图形处理单元 |
| APU | 产生音频并向 CPU 提供 frame/DMC IRQ 的处理单元 |
| Mapper | 把 CPU/PPU 地址窗口映射到卡带 ROM、RAM 或特殊逻辑的板级逻辑 |
| Nametable | `$2000`–`$3EFF` 中的 2 KiB 名称/属性数据区域 |
| OAM | 256 字节对象属性存储器，64 个四字节 sprite |
| CHR | 每 tile 16 字节的图形模式数据，平面低/高位各 8 字节 |
| Mirroring | 四个逻辑 nametable 如何映射到实际物理 nametable RAM |
| NMI | PPU vblank 等事件触发的不可屏蔽中断 |
| IRQ | 可由 APU、mapper 等来源触发、且受 CPU `I` 标志屏蔽的中断 |
| RDY/等待 | CPU 外部拉低时暂停总线周期；NES 参考 CPU 的具体等待行为要和系统实现一起验证 |
| Boot ROM | 商用 NES 通常没有用于启动游戏的独立 boot ROM；复位向量来自卡带映射空间 |

## 9. 开始前的安全边界

本目录中的“实验”是阅读和验证计划，不表示本目录已经运行了游戏、测试 ROM 或 FPGA 仿真。参考仓库是只读观察对象；后续若添加 C、Verilog、测试脚本或仿真波形，应放在项目允许的其他目录，而不要回写三个克隆仓库。文档本身不把参考 C 代码复制成项目 RTL，也不把 C 注释中的猜测升级成硬件规格。
